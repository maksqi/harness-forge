# Decisions

Architecture decision records (ADRs) and the **contract seed** — the shared names every document and every agent
must use. Edited only by the coordinator. When a doc and this file disagree, this file wins until the coordinator
resolves the conflict.

### Error envelope

`{ error: { code, message, status?, providerId?, retryAfterMs?, action?, details? } }` with `code` one of
`validation_error, unauthorized, forbidden, not_found, conflict, payload_too_large, provider_not_configured,
auth_invalid, rate_limited, model_not_found, context_overflow, provider_unreachable, provider_error, plugin_error,
internal_error, not_implemented` (501, used by Phase 0 route stubs). The envelope `status` is the upstream
provider status when relevant; the HTTP status is derived from `code` (`errorStatusByCode` in shared; e.g.
`auth_invalid` → 502 so a bad provider key never redirects to login). `action` one of `configure-provider | refresh-models | login | retry`.

### Server-sent events (`GET /api/events`)

`chat.created`, `chat.updated` (incl. title; data = the chat summary + `activeLeafId`, ADR-030), `chat.deleted`, `run.started`, `run.finished`, `provider.changed`,
`catalog.changed`, `plugin.changed`, `plugin.log`; Phase 7: `project.changed` (`{ id, project }`, `project` null =
deleted) and `key.rotated` (`{ keyVersion, rotatedAt, chatIds }`; every event stream closes after it); Phase 8:
`workspace.changed` (`{ projectId, chatId, batchId, source, paths }`, ADR-036; tool edits coalesced to at most one
event per second per chat); Phase 9: `queue.changed` (`{ chatId, items, removed? }`, ADR-042) and `run.started` gains
`origin?` and `userMessageId?` (a turn the server started from the queue); Phase 10: `task.changed` (`{ chatId, task }`,
at most one per second per task plus every status change, ADR-046) and `customization.changed` (`{ kind?, id?,
projectId? }`, ADR-044); `run.started.origin` gains `task`; Phase 11: `hooks.changed` (`{ projectId }`, null = personal or
plugin hooks, ADR-048), `project-trust.changed` (`{ projectId, pending }`, ADR-049) and `project-mcp.changed`
(`{ projectId, servers }`, ADR-050); `run.started.origin` gains `hook`; Phase 12: `marketplace.changed` (`{ id, marketplace }`,
`marketplace` null = removed, ADR-054; update badges reuse `plugin.changed`). Payload: `{ type, data, at }`. `run.finished` data includes
`awaitingApproval: boolean` (drives the amber sidebar dot; also persisted as `chats.pending_approval`).

### Chat request (`POST /api/chat`)

`{ chatId, message, trigger: 'submit-message' | 'regenerate-message', parentId?, messageId?, modelRef,
reasoningEffort, toolMode, imageOptions?, projectId? }` — only the last UI message is sent; the server owns history. `parentId` (a message id or
`null`) only with `submit-message` and a user message: the new message's parent (an edit = a new user message whose
parent is the edited message's parent); omitted = the chat's active leaf. `messageId` only with `regenerate-message`
(the reply to regenerate or the user message to answer). A user message sent with `messageId` is rejected (ADR-023).
`imageOptions` (`{ n?, aspectRatio?, editPrevious? }`, ADR-028) only with an image model or a chat model with image
output (`n` / `editPrevious` image models only). `projectId` (Phase 7) is honored only when the request creates the chat. Message metadata: `{ modelRef, startedAt, finishedAt?, durationMs?,
reasoningMs?, usage?, costUsd?, finishReason?, aborted?, error?, command?, image? }`. Phase 9: the request is unchanged
(file mentions are attachments, ADR-042); `POST /chat/:id/stop` returns the queued messages it dropped (`dropped`).
Phase 10: the request is unchanged; a command's `model` overrides one turn (`metadata.command.modelRef`) and its
`allowed-tools` narrow that turn (`metadata.command.allowedTools`, ADR-045); `metadata.command.source` is set for
`user` / `project` file commands only (plugin and harness invocations keep the v1.5 shape); the chat's Stop leaves background tasks
running (ADR-046). Phase 11: the request gains `outputStyle?` (a style name or null = automatic; saved when the request
creates the chat, ADR-051); a `UserPromptSubmit` or `SessionStart` hook that blocks answers 409 `hook-blocked` and
stores nothing; a project command with unapproved `!` spans answers 409 `untrusted`; `metadata.command` gains `kind`
(`command | skill`) and `inlined` (`{ shell, files }`, ADR-052). Phase 12: the request is unchanged; command and skill
names in `metadata.command.name` may be qualified (`<pluginId>:<name>`, ADR-053); the `skill` tool input gains `file?`
(a supporting file of a plugin or project skill).

### Chat export and backup formats

- Chat JSON export: `{ format: 'harness-forge.chat', version: 2, exportedAt, chat }` where `chat` = summary +
  settings + totals + `messages` (every version, `seq` order) + `parentIds` (aligned by index) + `activeLeafId`.
  Version 1 (linear, v1 exports) is still accepted by import. Markdown export = the active path.
  Phase 7: neither format carries `projectId` (projects are host-specific); imported chats have no project.
- Backup zip (`GET /api/data/export`): `manifest.json` (`{ format: 'harness-forge.backup', version: 1, ... }`,
  written last), `settings.json` (public settings, optional), `chats/<chatId>.json` (chat export v2),
  `files/index.json`, `files/<sha256>`; Phase 10: `customizations.json` (the personal agents, commands and skills as raw
  markdown, ADR-044); Phase 11: personal output styles join `customizations.json`; personal hooks, project approvals and
  project MCP variables are never in a backup; personal commands with `!` spans are restored turned off (ADR-052);
  Phase 12: marketplaces, Claude Code plugins, hook transcripts and import plans are never in a backup; the import result

### Tool output cap

A tool output whose serialized JSON exceeds `LIMITS.toolOutputBytes` (64 KB) is replaced by the server with
`{ truncated: true, originalBytes: number, preview: string }` (`preview` = the first 64 KB of the serialized JSON).
The web shows "Truncated by server" for any object output with `truncated: true`.
