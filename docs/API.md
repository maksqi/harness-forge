# HTTP API

The binding contract between `apps/web`, `apps/server` and `packages/shared`. `packages/shared` implements every
schema, route and helper named here **verbatim**; the server validates requests with these schemas
(`@hono/zod-validator`) and contract tests validate its responses against them. Names come from
[DECISIONS.md](./DECISIONS.md) (contract seed); architecture and flows are in [ARCHITECTURE.md](./ARCHITECTURE.md).

Contents: 1 Conventions · 2 Errors · 3 `packages/shared` naming contract · 4 Schemas · 5 Endpoints ·
6 Chat stream protocol · 7 Server events · 8 Route key index

## 1. Conventions

| Topic | Rule |
|---|---|
| Base path | Everything under `/api` (paths below omit it). Unknown `/api/*` paths return `404 not_found` JSON. |
| Format | JSON (`application/json; charset=utf-8`) request and response bodies unless a route says otherwise (SSE, UI message stream, multipart, binary). Request bodies are validated with zod; unknown keys are rejected (`.strict()`) except inside UI messages. A non-empty body sent to a JSON route must be `application/json` (or `+json`); routes with a multipart `form` also accept `multipart/form-data`; anything else -> `400 validation_error` (no form-encoded CSRF). |
| Auth | Session cookie `hf_session` (HttpOnly, SameSite=Strict). When a password is configured, every route except the public ones (marked **public**) returns `401 unauthorized` without a valid session. Without a password every request is authenticated. |
| CSRF | Origin check on every non-`GET`/`HEAD` request (ARCHITECTURE.md 10.2): a foreign `Origin` or a cross-site `Sec-Fetch-Site` -> `403 forbidden`. |
| Fresh auth | ADR-017. Sensitive routes (marked **fresh**) additionally require a login within the last 10 minutes when a password is set, else `403 forbidden` with `action: 'login'`. The proof is the session itself (`authAt`, `AuthStatus.freshUntil`): the web asks for the password, calls `POST /auth/login` and retries. |
| Success codes | `200` with a body; `201` for creations (`POST` that creates a resource); `204` for no body. |
| Errors | Every non-2xx response is a `HarnessErrorEnvelope` (section 2). |
| Timestamps | Integers, Unix epoch **milliseconds**. |
| Booleans in query strings | `true` / `false` (also `1` / `0`); coerced by the query schemas. |
| Pagination | Cursor based: `?cursor=<opaque>&limit=<1..100, default 50>` -> `{ items, nextCursor }`; `nextCursor` is `null` on the last page. Cursors are opaque base64url strings; an invalid cursor -> `400 validation_error`. Non-paginated lists return `{ items }`. |
| Ids | Chat: uuidv7 (lowercase, generated by the client with `createChatId()`). Message: `msg_` + 16 chars `[0-9A-Za-z]` (`createMessageId()`; assistant ids generated by the server, user ids by the client). File: `file_` + 16 chars. Share: `shr_` + 16 chars; share token: the 16-char share id suffix + 22 base64url chars (ADR-025). Plugin: `^[a-z0-9](?:[a-z0-9-]{0,38}[a-z0-9])?$`. Tool: `^[a-zA-Z0-9_-]{1,64}$`. Command: `^[a-z][a-z0-9-]{0,31}$`. MCP server: `^[a-z0-9](?:[a-z0-9-]{0,30}[a-z0-9])?$`. |
| Model ref | `providerId:modelId`, split on the **first** `:` (`ollama:llama3:8b`, `openrouter:anthropic/claude-sonnet-5`). Model refs travel only in bodies and query strings, **never in URL paths**; when a model must be addressed, `providerId` and `modelId` are separate fields. |
| Path params | URL-encoded by the client; `*` rest paths (plugin files) keep `/` separators and encode each segment. |
| Caching | JSON responses: `Cache-Control: no-store`. Icons and hashed assets: see their routes. |
| Request id | `X-Request-Id` response header on every response (ARCHITECTURE.md 12). |

## 2. Errors

### 2.1 Envelope and `HarnessError`

```ts
// Plain JSON error object: DTO fields (lastError, metadata.error, ...), the envelope content, and the return
// type of a provider's mapError() (plugin-sdk re-exports it)
type HarnessErrorInit = {                   // harnessErrorInitSchema
  code: HarnessErrorCode
  message: string            // human readable, English, safe to show; never contains secrets
  status?: number            // HTTP status reported by an UPSTREAM service (provider, MCP server, npm registry,
                             // install URL) when the error came from one, e.g. 401 -> UI badge "Error 401";
                             // the HTTP status of OUR response is derived from `code` (table 2.2)
  providerId?: string        // provider involved, when any
  retryAfterMs?: number      // for rate_limited (also sent as the Retry-After header, in seconds, rounded up)
  action?: HarnessErrorAction  // UI hint
  details?: unknown          // code-specific, see 2.3
}

// HTTP body of every non-2xx response, and the JSON inside in-stream `errorText` (section 6.5)
type HarnessErrorEnvelope = { error: HarnessErrorInit }   // harnessErrorEnvelopeSchema

// Throwable used by the server (thrown by services/routes, rendered by the error handler) and by the client
// (thrown by createApiClient on non-2xx)
class HarnessError extends Error implements HarnessErrorInit {
  constructor(init: HarnessErrorInit)
  readonly code: HarnessErrorCode           // + every other HarnessErrorInit field
  readonly requestId?: string               // client side: X-Request-Id of the failed response
  get httpStatus(): number                  // errorStatusByCode[code]
  toJSON(): HarnessErrorEnvelope
  static from(input: unknown): HarnessError // HarnessError -> itself; HarnessErrorInit or envelope object or
                                            // envelope JSON string; an Error whose `message` (or `responseBody`,
                                            // for the AI SDK APICallError) is envelope JSON; anything else ->
                                            // code 'internal_error' with a generic message
}
```

### 2.2 Codes, HTTP status, action

The HTTP status of an error response is determined by `code` (`errorStatusByCode` in `shared`). The web redirects
to `/login` only on `code === 'unauthorized'`, never on the HTTP status alone.

| `code` | HTTP | Typical `action` | Meaning |
|---|---|---|---|
| `validation_error` | 400 | - | Request failed zod validation or a semantic check (`details.issues`). |
| `unauthorized` | 401 | `login` | No valid session (or wrong password on `POST /auth/login`). |
| `forbidden` | 403 | `login` when fresh auth is missing | Origin check failed, fresh auth missing, operation not allowed for this resource (builtin plugin, read-only source). |
| `not_found` | 404 | - | Unknown route, chat, message, plugin, provider, file, tool, MCP server, icon, share link. Every failure of the public share routes is the same 404 (section 5.20). |
| `conflict` | 409 | - | State conflict: a run is active for the chat, id already exists, stale file `baseEtag`, password managed by `HF_PASSWORD`, another import or delete-all is running. |
| `payload_too_large` | 413 | - | Body, upload, zip, backup, share snapshot or file over the limit (`details.limitBytes`). |
| `provider_not_configured` | 400 | `configure-provider` | Provider unknown/disabled or required credentials missing. Returned before any streaming. |
| `auth_invalid` | 502 | `configure-provider` | Provider rejected the credentials (upstream 401/403). |
| `rate_limited` | 429 | `retry` | Upstream rate limit, login rate limit or share link rate limit; `retryAfterMs` when known. |
| `model_not_found` | 404 | `refresh-models` | Provider does not know the model (upstream 404). |
| `context_overflow` | 400 | - | Prompt exceeds the model context window even after trimming. |
| `provider_unreachable` | 502 | `retry` | Network failure reaching an upstream service: provider, MCP server, npm registry, install URL (ECONNREFUSED, ENOTFOUND, timeout). |
| `provider_error` | 502 | `retry` | Any other upstream error (provider, MCP server, npm registry, install URL). |
| `plugin_error` | 500 | - | Plugin code threw, timed out, or failed to load/build (`details.pluginId`). |
| `internal_error` | 500 | `retry` | Unexpected server error (`details.requestId`). Message is generic; details are logged. |
| `not_implemented` | 501 | - | Phase 0 route and service stubs. Every route is implemented now; the code stays in the contract. |

`HarnessErrorAction` = `configure-provider | refresh-models | login | retry`.

### 2.3 `details` by code

| Code | `details` shape |
|---|---|
| `validation_error` | `{ issues: Array<{ path: Array<string \| number>; message: string; code: string }> }` (zod issues, flattened) |
| `conflict` | `{ reason: 'run-active' \| 'exists' \| 'stale' \| 'disabled' \| 'env-password' \| 'insecure-bind' \| 'busy', chatId?: string }` (`busy`: another import or delete-all is running, section 5.19) |
| `payload_too_large` | `{ limitBytes: number }` |
| `plugin_error` | `{ pluginId: string; phase?: 'load' \| 'setup' \| 'dispose' \| 'hook' \| 'tool' \| 'build' \| 'install' }` |
| `internal_error` | `{ requestId: string }` |
| others | omitted, or `{ upstream?: string }` (a short, redacted upstream message) |

Provider error mapping (chat pipeline and provider calls): `provider.mapError(err)` first; then upstream 401/403 ->
`auth_invalid`; 429 -> `rate_limited`; 404 -> `model_not_found`; context-length errors -> `context_overflow`;
`ECONNREFUSED` / `ENOTFOUND` / `ETIMEDOUT` / fetch timeout -> `provider_unreachable`; everything else ->
`provider_error`. `providerId` and `status` are set when known.

## 3. `packages/shared` naming contract

C1+C2 (one agent, both contract packages) implements exactly these exports (file layout inside
`packages/shared/src` is free; everything is re-exported from the package root).

### 3.1 Schemas and types

- Every DTO in section 4 is a zod v4 schema named `<camelCase>Schema` with an inferred PascalCase type of the same
  base name: `export const chatSummarySchema = z.object({...})` +
  `export type ChatSummary = z.infer<typeof chatSummarySchema>`.
- Enums: `<camelCase>Schema = z.enum([...])` + type (`toolModeSchema` / `ToolMode`).
- Generic helpers: `listResponseSchema(item)` -> `{ items: T[] }`, `cursorPageSchema(item)` -> `{ items: T[];
  nextCursor: string | null }`, types `ListResponse<T>`, `CursorPage<T>`.
- Request schemas that are not DTOs use the suffixes `Query`, `Params`, `Body`/`Update`/`Input` as listed in
  section 4 (`chatsQuerySchema`, `chatUpdateSchema`, `customModelInputSchema`, ...).

### 3.2 Package layering and plugin data shapes

`@harness-forge/plugin-sdk` depends on `@harness-forge/shared` (`workspace:*`); `shared` never imports
`plugin-sdk` (no cycle). Therefore `shared` owns every JSON shape that crosses the HTTP boundary, including the
plugin **data** shapes that API DTOs embed (shapes defined in [PLUGINS.md](./PLUGINS.md), plan Appendix A).
`plugin-sdk` re-exports them unchanged and adds the runtime contract (`PluginContext`, `ProviderDefinition`,
`ToolDefinition`, `CommandDefinition`, `HookMap`, `PluginModule`, `definePlugin`, `PLUGIN_API_VERSION`,
`settingsValuesSchema()`, ...). Plugin authors keep importing everything from `@harness-forge/plugin-sdk`.

| Type (name fixed) | Schema in `shared`, re-exported by `plugin-sdk` | Used in |
|---|---|---|
| `PluginManifest` | `pluginManifestSchema` | `PluginDetail`, `PluginInspection`, `PluginDraft`, `PluginManifestUpdate` |
| `DeclarativeProvider` | `declarativeProviderSchema` | `DraftTestRequest` (and `PluginManifest.contributes.providers`) |
| `McpServerDecl` | `mcpServerDeclSchema` | `PluginManifest.contributes.mcpServers` |
| `CredentialField` | `credentialFieldSchema` | `ProviderSummary.credentialFields` |
| `ModelInfo` | `modelInfoSchema` | `DraftTestResult.models`, `PluginManifest.contributes.models` |
| `SettingsSchema` | `settingsSchemaSchema` | `PluginSettingsView.schema`, `PluginManifest.settings` |
| `ReasoningEffort`, `ToolPolicy` | `reasoningEffortSchema`, `toolPolicySchema` | everywhere |
| `HarnessErrorInit`, `HarnessErrorCode`, `HarnessErrorAction` | section 2 | `ProviderDefinition.mapError()` |

Note: `ai` 7 also exports a type named `ModelInfo`; always import `ModelInfo` from `@harness-forge/shared` or
`@harness-forge/plugin-sdk`, never from `ai`.

### 3.3 Route table

```ts
export type HttpMethod = 'GET' | 'POST' | 'PUT' | 'PATCH' | 'DELETE'
export type ApiResponseSpec = z.ZodType | 'empty' | 'sse' | 'ui-message-stream' | 'binary'

export type ApiModule =
  | 'health' | 'auth' | 'settings' | 'events' | 'providers' | 'credentials' | 'models' | 'icons' | 'chats'
  | 'chat' | 'files' | 'tools' | 'mcp' | 'commands' | 'plugins' | 'pluginInstall' | 'pluginDrafts' | 'pluginFiles'
  | 'data' | 'shares'

export interface ApiRouteDef {
  module: ApiModule         // = the key prefix; server route module file = kebab-case of it (plugin-install.ts)
  method: HttpMethod
  path: `/${string}`        // relative to /api, Hono syntax ('/chats/:id'); a trailing '*' is the rest path,
                            // bound to params.path ('/plugins/:id/files/*')
  public?: true             // no session required (default: session required)
  fresh?: true              // ALWAYS requires fresh auth when a password is set; conditional cases
                            // (mcp.create / mcp.update with stdio, pluginInstall.install of a plugin that
                            // requires trust, pluginDrafts.create / pluginDrafts.updateManifest with a stdio MCP
                            // server, plugins.reload of a code plugin, pluginFiles.write / pluginFiles.remove of a
                            // plugin that runs code) are enforced by the server only
  params?: z.ZodType        // path params
  query?: z.ZodType
  body?: z.ZodType          // JSON body
  form?: z.ZodType          // multipart/form-data fields other than the file part named `file`;
                            // a route with `form` accepts multipart (and JSON too when `body` is also set)
  response: ApiResponseSpec // zod schema = JSON body; 'empty' = 204; 'sse' = text/event-stream (ServerEvent);
                            // 'ui-message-stream' = AI SDK UI message stream; 'binary' = raw bytes
  status?: 200 | 201 | 204  // success status; default 200, 204 for 'empty'
}

export const apiRoutes = {
  'health.get': { module: 'health', method: 'GET', path: '/health', public: true, response: healthSchema },
  // ... one entry per endpoint, keyed '<module>.<action>' (section 8 lists every key)
} as const satisfies Record<string, ApiRouteDef>

export type ApiRouteKey = keyof typeof apiRoutes
```

The route table has no flag for secret path params: share tokens (`/share/:token...`) are masked by the server's
access log and `redactText`, not by the route table.

Module names (camelCase of the server route module file): `health`, `auth`, `settings`, `events`, `providers`,
`credentials`, `models`, `icons`, `chats`, `chat`, `files`, `tools`, `mcp`, `commands`, `plugins`,
`pluginInstall`, `pluginDrafts`, `pluginFiles`, `data`, `shares` (`shares.ts` also serves the public
`/share/:token` routes). Action verbs: `list` (collection GET), `get` (item GET), `create`, `update`, `remove`, plus
specific verbs (`test`, `refresh`, `stop`, `switchBranch`, `deleteAll`, ...).

### 3.4 Client

```ts
export interface ApiClientOptions {
  baseUrl?: string          // default '/api'
  fetch?: typeof fetch      // default globalThis.fetch; the web wraps it (401 unauthorized -> /login)
}
export function createApiClient(options?: ApiClientOptions): ApiClient

// client.<module>.<action>(input?) for every route key '<module>.<action>'
type ApiCallInput<R extends ApiRouteDef> = {
  params?: z.input<R['params']>   // required when the route has params
  query?: z.input<R['query']>
  body?: z.input<R['body']>       // JSON body
  form?: FormData                 // multipart body (routes with `form`)
  signal?: AbortSignal
  headers?: Record<string, string>
}
// Result: zod schema -> Promise<z.output<schema>> (typed, not re-validated at runtime)
//         'empty' -> Promise<void>;  'sse' | 'ui-message-stream' | 'binary' -> Promise<Response> (raw)
```

Examples: `client.chats.list({ query: { q: 'foo' } })`, `client.chats.get({ params: { id } })`,
`client.credentials.set({ params: { id: 'anthropic' }, body: { values: { apiKey } } })`,
`client.files.upload({ form })`, `client.pluginFiles.read({ params: { id, path: 'src/index.ts' } })`,
`client.chats.switchBranch({ params: { id }, body: { messageId } })`, `client.data.import({ form })`,
`client.data.export({ query: { files: false } })` (a raw `Response`), `client.shares.view({ params: { token } })`.

Behavior: sends `credentials: 'same-origin'`, `Accept: application/json`, `Content-Type: application/json` for JSON
bodies; non-2xx -> throws `HarnessError` (from the envelope, `requestId` from `X-Request-Id`); a network failure or a
non-envelope body -> `HarnessError` with code `internal_error`.

| `iconParamsSchema` / `IconParams` | `{ slug: IconSlug }` |
| `shareParamsSchema` / `ShareParams` | `{ id: ShareId }` |

| `shareFileParamsSchema` / `ShareFileParams` | `{ token: ShareToken; fileId: FileId }` (same `404` rule) |
| `fileUploadFormSchema` / `FileUploadForm` | `{}` (only the file part `file`) |

### 4.16 Bulk data (backup, import, delete-all)

ADR-024. A backup is a zip; every chat in it is exactly its `ChatExport` (version 2, section 4.7).

```ts
type DataSummary = {                    // dataSummarySchema (GET /data)
  chats: number                         // every chat, archived ones included
  archivedChats: number
  messages: number                      // every message version
  files: number                         // uploaded files (rows)
  fileBytes: number                     // bytes of the uploaded files
}

type DataExportQuery = {                // dataExportQuerySchema (GET /data/export)
  files?: boolean                       // default true: attachments referenced by message parts
  settings?: boolean                    // default true: the public Settings (settings.json)
}

type DataConflictPolicy = 'skip' | 'copy'   // dataConflictPolicySchema: a chat whose id already exists is kept
                                            // ('skip') or imported again under new ids ('copy')

type DataImportForm = {                 // dataImportFormSchema; multipart fields next to the upload part `file`
  onConflict?: DataConflictPolicy       // default 'skip'
  restoreSettings?: boolean             // default false; 'true' | 'false' | '1' | '0'
}

type DataImportItem = {                 // dataImportItemSchema; one chat of the upload
  sourceId: string                      // the chat id in the upload (<= 80 chars)
  chatId: ChatId | null                 // the stored chat: same id (imported, skipped), new id (copied); null if failed
  title: string | null
  status: 'imported' | 'copied' | 'skipped' | 'failed'   // dataImportStatusSchema
  error?: string                        // why it failed, safe to show (<= 500 chars)
}

type DataImportResult = {               // dataImportResultSchema (POST /data/import)
  kind: 'backup' | 'chat'               // dataImportKindSchema: a backup zip, or one chat JSON (ChatExportAny)
  counts: {
    imported: number; copied: number; skipped: number; failed: number
    filesImported: number               // attachments stored by this import
    filesReused: number                 // attachments whose content was already stored
    filesMissing: number                // attachments referenced by a chat but absent from the backup
  }
  settingsRestored: boolean
  items: DataImportItem[]
  warnings: string[]                    // <= 100, each <= 300 chars: unknown entries, missing files, settings keys
}                                       // that failed validation

type DataDeleteBody = {                 // dataDeleteBodySchema (POST /data/delete); strict
  confirm: 'DELETE'                     // typed confirmation
  files?: boolean                       // default false: also delete every uploaded file (rows and blobs)
  usage?: boolean                       // default false: also delete the usage rows (else kept with
}                                       // chat_id = NULL, as for DELETE /chats/:id)

type DataDeleteResult = {               // dataDeleteResultSchema; what was deleted
  chats: number
  messages: number                      // every version
  files: number; fileBytes: number      // 0 unless files: true
  usageRows: number                     // 0 unless usage: true
}

type BackupManifest = {                 // backupManifestSchema; manifest.json, written last (exact counts)
  format: 'harness-forge.backup'
  version: 1                            // a newer version is refused by the import
  exportedAt: Timestamp
  appVersion: string                    // harness-forge version that wrote it (<= 64 chars)
  chatExportVersion: 2                  // version of every chats/<chatId>.json
  includes: { files: boolean; settings: boolean }
  counts: { chats: number; messages: number; files: number; fileBytes: number }
}

  id: FileId                            // the id in the part URLs (/api/files/<id>); remapped on import when needed
  sha256: Sha256Hex                     // the blob entry files/<sha256>; re-hashed on import
  name: string                          // 1..255 chars
  mime: string
  size: number                          // <= 20 MB
  createdAt: Timestamp
}

type BackupFileIndex = { items: BackupFileEntry[] }   // backupFileIndexSchema; files/index.json, <= 50000 items
```

Backup zip layout (`GET /data/export`; every entry mode 0644 with mtime = `exportedAt`):

| Entry | Content |
|---|---|
| `manifest.json` | `BackupManifest`, written last |
| `settings.json` | the public `Settings` (only with `settings=true`; restored only on opt-in) |
| `chats/<chatId>.json` | the `ChatExport` (version 2) of every chat, archived ones included |
| `files/index.json` | `BackupFileIndex` (only with `files=true`) |
| `files/<sha256>` | attachment bytes, deduplicated by sha256: stored for images and PDF, deflated for text |

Never in a backup: secrets, credentials, the password, plugins, MCP servers, model and tool preferences, share links,
usage rows (`totals` of imported chats restart at 0; `metadata.usage` of each message is kept). An import also
accepts the same layout inside a single top-level folder.

### 4.17 Share links

ADR-025. A share is a sanitized **snapshot** of a chat's active path, never a live view.

```ts
type ShareOptions = {                   // shareOptionsSchema; defaults apply at creation
  reasoning: boolean                    // default false: reasoning parts
  toolDetails: boolean                  // default false: tool inputs and outputs, each value <= 16384 chars
                                        // (tool names and states are always shown)
  attachments: boolean                  // default true: attachments (GET /share/:token/files/:fileId)
}

type ShareOptionsInput = Partial<ShareOptions>  // shareOptionsInputSchema; strict, no defaults: a key not sent keeps
                                                // its default (create) or its current value (update)

type ShareCreate = {                    // shareCreateSchema (POST /shares); strict
  chatId: ChatId
  title?: string                        // 1..200 chars; default: the chat title
  options?: ShareOptionsInput
  expiresAt?: Timestamp | null          // in the future, at most 365 days ahead; null / omitted = never expires
}

type ShareUpdate = {                    // shareUpdateSchema (PATCH /shares/:id); strict, at least one key
  title?: string | null                 // null = back to the chat title
  options?: ShareOptionsInput           // applies to the share page at once
  expiresAt?: Timestamp | null          // same rules as ShareCreate; null removes the expiry
  refresh?: true                        // re-snapshot the chat's current active path ("Update snapshot")
}

type SharesQuery = { chatId?: ChatId }  // sharesQuerySchema (GET /shares); omitted = every share link

type ShareSummary = {                   // shareSummarySchema; a share link as its owner sees it
  id: ShareId
  chatId: ChatId
  chatTitle: string | null              // the chat's current title
  title: string | null                  // custom title; null = the chat title of the snapshot
  options: ShareOptions
  path: string                          // '/share/<token>' (recomputed, never stored); the web copies
                                        // location.origin + path
  messageCount: number                  // messages in the snapshot
  snapshotAt: Timestamp
  outdated: boolean                     // the chat changed after snapshotAt
  expiresAt: Timestamp | null
  expired: boolean
  createdAt: Timestamp
}

type SharePart =                        // sharePartSchema, discriminated on `type` (the allowlist)
  | { type: 'text'; text: string }
  | { type: 'reasoning'; text: string }                                   // only with options.reasoning
  | { type: 'file'; mediaType: string; filename?: string; url: string }  // only with options.attachments; url =
                                                                          // a share file URL or a raster data URL
  | { type: 'source-url'; sourceId: string; url: string; title?: string }
  | { type: 'source-document'; sourceId: string; title: string; mediaType: string; filename?: string }
  | { type: 'tool'; toolName: string                                      // static and dynamic (MCP) tools
      status: 'done' | 'error' | 'denied' | 'stopped'                     // shareToolStatusSchema
      input?: unknown; output?: unknown; errorText?: string }             // only with options.toolDetails

type ShareMessage = {                   // shareMessageSchema; user and assistant messages only, no ids
  role: 'user' | 'assistant'
  modelRef?: ModelRef                   // assistant: the model that answered
  command?: { name: CommandName }       // user: the slash command invoked (never its expansion)
  status?: 'failed' | 'stopped'         // the reply ended with an error (no details) or was stopped
  parts: SharePart[]                    // <= 1000
}

type ShareSnapshot = {                  // shareSnapshotSchema; stored (<= 10 MB), file URLs '/api/files/<id>'
  title: string | null                  // title shown on the share page
  messages: ShareMessage[]
}

type ShareView = ShareSnapshot & {      // shareViewSchema (GET /share/:token); file URLs rewritten to
  snapshotAt: Timestamp                 // '/api/share/<token>/files/<fileId>'
  options: ShareOptions
}
```

The sanitizer is an allowlist. Dropped when the snapshot is taken: system messages, chat and global instructions,
`metadata.error` (a failed reply keeps only `status: 'failed'`), usage and cost, `command.expansion`, provider
metadata, approvals, `data-*` and `step-start` parts, `reasoning-file` parts, unknown parts, and data URLs that are not
raster images.

## 5. Endpoints

Grouped by server route module (`apps/server/src/http/routes/<module>.ts`), exactly as in DECISIONS.md. Each entry:
route key, auth (**public** / session / **fresh**), input, success response, specific errors.

Implicit errors (not repeated below): `401 unauthorized` on every non-public route without a session;
`403 forbidden` on every non-`GET` route failing the Origin check; `400 validation_error` on every route with
params/query/body (except the public share routes, which answer `404`, section 5.20); `413 payload_too_large` when a
body exceeds its limit; `500 internal_error`.

### 5.1 `health.ts`

**`GET /health`** — `health.get` · public
- Response `200 Health`. Used by Docker `HEALTHCHECK`, gate scripts and Settings → About.

### 5.2 `auth.ts`

**`GET /auth/status`** — `auth.status` · public
- Response `200 AuthStatus`.

**`POST /auth/login`** — `auth.login` · public
- Body `LoginBody`.
- Response `200 AuthStatus` + `Set-Cookie: hf_session=...`. When no password is configured: `200` with
  `enabled: false, authenticated: true`, no cookie.
- Errors: `401 unauthorized` (wrong password, message "Invalid password"); `429 rate_limited` (`retryAfterMs`,
  `Retry-After`). The limiter counts per client address: the TCP peer, unless the peer is a reverse proxy trusted by
  `HF_TRUST_PROXY` (ADR-026), in which case the client is read from `X-Forwarded-For`; without `HF_TRUST_PROXY` every
  client behind a proxy shares the proxy's address (ARCHITECTURE.md 10.1).

**`POST /auth/logout`** — `auth.logout` · public
- Response `204`, clears the cookie (`Max-Age=0`). Idempotent.

**`PUT /auth/password`** — `auth.setPassword` · **fresh**
- Body `PasswordUpdate`. `newPassword: null` removes the password.
- Response `200 AuthStatus`; the session epoch is incremented (all other sessions end) and a new cookie is set
  for the caller (none when the password was removed).
- Errors: `403 forbidden` (`currentPassword` missing or wrong); `409 conflict` (`reason: 'env-password'` when
  `HF_PASSWORD` is set; `reason: 'insecure-bind'` when removing the password on a non-loopback bind without
  `HF_INSECURE=1`).

### 5.6 `credentials.ts`

**`PUT /providers/:id/credentials`** — `credentials.set`

- Secret fields are encrypted into `secrets` (scope `provider:<id>`, name = field key); other fields go to

- Response `200 ProviderSummary`. **Never echoes secret values** (only `SecretState`). Clears `lastError`, emits

- Params `{ id: ProviderId }`.
- Response `200 ProviderSummary`. Removes every stored value of the provider (env fallbacks keep working). Emits

- Errors: `404 not_found`.

**`POST /providers/:id/models/refresh`** — `models.refresh`

- Errors: `404 not_found`; `400 provider_not_configured`; upstream errors mapped as in 2.3 (`auth_invalid`,

**`PUT /model-prefs`** — `models.updatePrefs`
- Body `ModelPrefsUpdate` (the model is addressed by `providerId` + `modelId`, never by a path).
- Response `200 CatalogModel`. Emits `catalog.changed`.
- Errors: `404 not_found` (provider unknown, or model not in the catalog).

**`POST /custom-models`** — `models.addCustom`
- Body `CustomModelInput`. Creates or replaces the custom model (`model_prefs.custom = 1`, `info`).
- Response `201 CatalogModel` (`custom: true`, `source: 'custom'`). Emits `catalog.changed`.
- Errors: `404 not_found` (unknown provider).

**`DELETE /custom-models?providerId=&modelId=`** — `models.removeCustom`
- Query `CustomModelKey`.
- Response `204`. Emits `catalog.changed`.
- Errors: `404 not_found` (no custom model with that key).

### 5.9 `chats.ts`

**`GET /chats`** — `chats.list`
- Query `ChatsQuery` (`cursor`, `limit`, `q`, `archived`).
- Response `200 CursorPage<ChatSummary>`, ordered by `updatedAt` desc, `id` desc; `snippet` set when `q` is given.
  The search covers every message version, so a snippet may come from a version that is not on the active path.

**`POST /chats`** — `chats.create`
- Body `ChatCreate`. Without `messages` it creates an empty chat; with `messages` it imports them (e.g. the
  `chat` of a JSON export): deep-validated with `validateUIMessages`, `seq` from array order, invalid or already
  used message ids replaced with new ones (`parentIds` and `activeLeafId` follow), pending approvals resolved as
  denied. Without `parentIds` the import is linear; with `parentIds` every parent must be the id of an earlier
  message and the ids must be unique. The active leaf is the most recent leaf under `activeLeafId` (default: the
  last message). Body limit 20 MB (imports), <= 2000 messages.
- Response `201 ChatDetail`. Emits `chat.created`.
- Errors: `409 conflict` (`reason: 'exists'`, id already used); `400 validation_error` (a parent that is not an
  earlier message, duplicate ids, an unknown `activeLeafId`; `details.issues` carry the field path).
- Note: the normal "new chat" flow does not call this: the web generates a uuidv7 and the first `POST /chat`
  creates the chat.

**`GET /chats/:id`** — `chats.get`
- Params `{ id: ChatId }`.
- Response `200 ChatDetail`: `messages` = the active path (first message -> active leaf, `seq` order), `branches` =
  the versions of the path messages that have siblings. During a run the path ends at the message committed when the
  run started (section 6.6).
- Errors: `404 not_found`.

**`PATCH /chats/:id`** — `chats.update`
- Params `{ id: ChatId }`. Body `ChatUpdate`.
- Response `200 ChatSummary`. Emits `chat.updated`. A `title` sets `titleSource: 'user'` (never overwritten by
  auto titles).
- Errors: `404 not_found`.

**`DELETE /chats/:id`** — `chats.remove`
- Params `{ id: ChatId }`.
- Stops an active run first, deletes the chat, its messages (every version) and its share links (cascade); usage
  rows are kept with `chat_id = NULL`; uploaded files are kept (content-addressed, shared).
- Response `204`. Emits `chat.deleted`.
- Errors: `404 not_found`.
- Note: "Undo" in the UI delays this call (toast), the server has no soft delete.

**`GET /chats/:id/export?format=md|json`** — `chats.export` · response `'binary'`
- Params `{ id: ChatId }`. Query `ChatExportQuery`.
- Response `200` with `Content-Disposition: attachment; filename="<title-slug>-<yyyy-mm-dd>.<md|json>"`:
  - `format=json`: `application/json; charset=utf-8`, body `ChatExport` (version 2: every message version,
    `parentIds`, `activeLeafId`).
  - `format=md`: `text/markdown; charset=utf-8`, the active path: `# <title>`, an export line (date, model), then one
    section per message (`## User` / `## Assistant (<modelRef>)`): text parts verbatim, reasoning as a `> ` quote
    block, tool calls as `**Tool** \`<name>\` (<state>)` with input and output in fenced `json` blocks (output
    truncated at 4 KB), files as `[name](url)`.
- Errors: `404 not_found`.

**`POST /chats/:id/branch`** — `chats.switchBranch`
- Params `{ id: ChatId }`. Body `ChatBranchBody` (`messageId`: any message of the chat, ADR-023).
- Makes the most recent leaf under `messageId` (the highest `seq` in its subtree) the active leaf. `pendingApproval`
  is recomputed from the new path (approvals on other versions stay pending and are live again when their version is
  shown); `updatedAt` is not changed.
- Response `200 ChatDetail` (the new path and its `branches`). Emits `chat.updated`.
- Errors: `404 not_found` (unknown chat, or `messageId` not in the chat); `409 conflict` (`reason: 'run-active'`,
  `chatId`) while a run holds the chat, in any phase.

### 5.10 `chat.ts`

**`POST /chat`** — `chat.send` · response `'ui-message-stream'`
- Body `ChatRequestBody` (max 2 MB).
- Response `200` AI SDK v7 UI message stream (section 6). Errors that happen before the stream starts are normal
  JSON error responses: `400 provider_not_configured` (action `configure-provider`); `404 not_found` (`parentId` or
  `messageId` not in the chat, or a continuation that is not the active leaf); `409 conflict` (`reason: 'run-active'`,
  `chatId`; `reason: 'exists'` when the new user message id is already stored); `400 validation_error` (including
  `validateUIMessages` failures, file parts whose `url` is not `/api/files/<id>`, a user message sent with
  `messageId`, `parentId` on a regenerate or a continuation, and a regenerate whose target is not answered by a user
  message). Section 6.2 lists what each action sends.

**`GET /chat/:id/stream`** — `chat.resume` · response `'ui-message-stream'`
- Params `{ id: ChatId }`. This is the default reconnect URL of `DefaultChatTransport` (`{api}/{chatId}/stream`).
- Response `200` stream (the active run replayed from its first chunk, then live chunks), or
  `204 No Content` when there is nothing to resume (idle or unknown chat).

**`POST /chat/:id/stop`** — `chat.stop`
- Params `{ id: ChatId }`. No body.
- Response `200 ChatStopResult` (`stopped: false` when no run was active). The run is aborted, the partial message
  is persisted with `metadata.aborted = true`, `run.finished` is emitted with `outcome: 'aborted'`.

### 5.11 `files.ts`

**`POST /files`** — `files.upload` · multipart
- Body `multipart/form-data` with exactly one file part named `file` (form schema `fileUploadFormSchema` = no other
  fields).
- Limits: 20 MB per file (`413 payload_too_large`). Allowed MIME families: `image/*`, `application/pdf`,
  `text/*`. The type is checked against the content (magic bytes for images and PDF, valid UTF-8 for text);
  mismatches are rejected. The name is sanitized (no path separators or control characters, <= 255 chars).
- Stored content-addressed at `data/files/<aa>/<sha256>` (deduplicated); every upload gets its own `files` row.
- Response `201 FileRef`.
- Errors: `400 validation_error` (missing part, several files, disallowed or mismatched type), `413`.

**`GET /files/:id`** — `files.get` · response `'binary'`
- Params `{ id: FileId }`.
- Response `200` bytes with `Content-Type: <mime>` (`text/*` with `; charset=utf-8`), `Content-Length`,
  `ETag: "<sha256>"`, `Cache-Control: private, max-age=31536000, immutable`, `X-Content-Type-Options: nosniff`,
  `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; sandbox` (PDF: same without
  `sandbox`), and `Content-Disposition: inline; filename*=UTF-8''<name>` for PNG, JPEG, GIF, WebP, AVIF and PDF,
  `attachment` for everything else (SVG and text included). A matching `If-None-Match` gets `304 Not Modified`.
- Errors: `404 not_found`.

### 5.15 `plugins.ts`

**`GET /plugins`** — `plugins.list`
- Response `200 ListResponse<PluginSummary>`: builtins first, then by id. The Plugins tab filters
  (`/plugins?filter=all|providers|tools|mcp|commands|disabled` on the web route) are applied client-side from

**`GET /plugins/:id`** — `plugins.get`
- Params `{ id: PluginId }`.
- Response `200 PluginDetail`.
- Errors: `404 not_found`.

**`DELETE /plugins/:id?keepData=true|false`** — `plugins.remove`
- Params `{ id: PluginId }`. Query `PluginRemoveQuery`.
- Disposes the plugin, removes `data/plugins/<id>` (for `link` only the link record; the user's folder is never
  touched) and the `plugins` row. Unless `keepData=true` also purges `plugin_settings`, `plugin_kv`, secrets of
  scope `plugin:<id>`, the private data dir `data/plugins/.data/<id>/`, and credentials/configs of the plugin's
  providers.
- Response `204`. Emits `plugin.changed` (`plugin: null`), `provider.changed`, `catalog.changed` as applicable.
- Errors: `404 not_found`; `403 forbidden` (builtin).

**`POST /plugins/:id/enable`** — `plugins.enable`
- Params `{ id: PluginId }`. Sets `enabled = true` and loads the plugin.
- Response `200 PluginDetail` with the resulting `state` (`active`, `untrusted`, `incompatible` or `error`; a load
  failure is reported in the DTO, not as an HTTP error). Emits `plugin.changed` (+ `catalog.changed`).
- Errors: `404 not_found`.

**`POST /plugins/:id/disable`** — `plugins.disable`
- Params `{ id: PluginId }`. Sets `enabled = false` and disposes the plugin (section 6.4 of ARCHITECTURE.md).
- Response `200 PluginDetail` (`state: 'disabled'`). Emits `plugin.changed`, `catalog.changed`,
  `provider.changed` as applicable.
- Errors: `404 not_found`.

**`POST /plugins/:id/reload`** — `plugins.reload` · **fresh** when the plugin is a code plugin
- Params `{ id: PluginId }`. Dispose + load again (cache-busted import).
- Response `200 PluginDetail` with the resulting state. Emits `plugin.changed`.
- Errors: `404 not_found`; `409 conflict` (`reason: 'disabled'`).

**`GET /plugins/:id/settings`** — `plugins.getSettings`
- Params `{ id: PluginId }`.
- Response `200 PluginSettingsView` (`schema: null` when the plugin has no settings).
- Errors: `404 not_found`.

**`PUT /plugins/:id/settings`** — `plugins.updateSettings`
- Params `{ id: PluginId }`. Body `PluginSettingsUpdate`, validated against the plugin's `SettingsSchema`
  (issues carry the property path). Secret properties are encrypted (scope `plugin:<id>`, name
  `settings.<key>`); other values go to `plugin_settings`.
- Response `200 PluginSettingsView`. The plugin's `ctx.settings.onChange` handlers run (guarded).
- Errors: `404 not_found`; `400 validation_error` (also when the plugin has no settings schema).

**`GET /plugins/:id/icon`** — `plugins.icon` · response `'binary'`
- Params `{ id: PluginId }`. Serves the manifest's file icon (`.svg` or `.png` inside the plugin dir; realpath
  checked). For `lobe:<slug>` icons: `302` to `/api/icons/lobe/<slug>`.
- Headers: `Content-Type: image/svg+xml | image/png`, `Cache-Control: private, max-age=31536000, immutable` (DTO
  URLs carry `?v=<first 8 hex of the file sha256>`), `X-Content-Type-Options: nosniff`,
  `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'`.
- Errors: `404 not_found` (unknown plugin or no icon).

**`GET /plugins/:id/logs`** — `plugins.logs`
- Params `{ id: PluginId }`. Query `PluginLogsQuery`.
- Response `200 ListResponse<PluginLogEntry>` from the in-memory ring buffer (oldest first). Live entries arrive
  as `plugin.log` events.
- Errors: `404 not_found`.

### 5.16 `plugin-install.ts`

**`POST /plugins/inspect`** — `pluginInstall.inspect` · JSON or multipart
- Body `PluginInspectBody` (JSON), or `multipart/form-data` with the zip in part `file` (<= 20 MB).
- Fetches/extracts into `plugins/.staging/<uuid>` with all install guards, validates, reports, then deletes the
  staging dir. Nothing is installed.
- Response `200 PluginInspection`.
- Errors: `400 validation_error` (invalid manifest, zip guard violation, integrity mismatch, folder is not a
  plugin, reserved id); `413 payload_too_large`; upstream fetch failures as `not_found` (npm 404),
  `provider_unreachable` or `provider_error` with `status`.

**`POST /plugins/install`** — `pluginInstall.install` · JSON or multipart · **fresh** when the plugin requires trust
- Body `PluginInstallBody` (JSON), or multipart: part `file` (zip) + `PluginInstallForm` fields.
- Fresh auth is required whenever the plugin requires trust (code plugin, or a declarative plugin with a stdio MCP
  server; ADR-017), with or without `trust`. A code plugin installed without `trust` ends `untrusted` (inert) until
  `POST /plugins/:id/trust`.
- Installs via staging + atomic swap (ARCHITECTURE.md 6.5). Same id and same source = update (the previous
  version is restored if the new one fails to load).
- What was reviewed is what gets installed: `sha256` (optional) is the hash shown by `inspect`. The server also
  remembers the hash of npm and folder sources inspected in the last 30 minutes; when the source now yields other
  files (a moved npm tag or range, an edited folder), the install is refused. Zip uploads and URL installs are
  pinned by their bytes / SRI integrity.
- Response `201 PluginDetail`. Emits `plugin.changed` (+ `catalog.changed`, `provider.changed`).
- Errors: as `inspect`; `400 validation_error` (incompatible `engines.harness`); `403 forbidden` (reserved or
  builtin id, fresh auth missing); `409 conflict` (`reason: 'exists'`, id installed from a different source;
  `reason: 'stale'`, the package changed since it was reviewed).

**`POST /plugins/:id/trust`** — `pluginInstall.trust` · **fresh**
- Params `{ id: PluginId }`. Body `PluginTrustBody`.
- Pins `trusted_hash` (for `link`: pins the realpath) and reloads if enabled.
- Response `200 PluginDetail`.
- Errors: `404 not_found`; `409 conflict` (`reason: 'stale'`, `sha256` differs from the current hash: the files
  changed since inspection).

**`GET /plugins/:id/export`** — `pluginInstall.export` · response `'binary'`
- Params `{ id: PluginId }`.
- Response `200 application/zip`, `Content-Disposition: attachment; filename="<id>-<version>.zip"`: the plugin
  directory (without build output, `node_modules`, `.git`), installable with `POST /plugins/install`.
- Errors: `404 not_found`; `403 forbidden` (builtin).

### 5.17 `plugin-drafts.ts`

**`POST /plugins`** — `pluginDrafts.create` · **fresh** when the manifest declares a stdio MCP server
- Body `PluginDraft`. Creates a declarative plugin (`source: 'created'`, `kind: 'declarative'`) through staging:
  `plugin.json` (+ `iconFile`, SVG sanitized), loads it, then saves `credentials` as provider credentials (never in
  `plugin.json`) and validates / lists them in the background like `PUT /providers/:id/credentials`. A manifest that
  declares a stdio MCP server requires fresh auth and is trusted on creation.
- Response `201 PluginDetail`. Emits `plugin.changed`, `provider.changed`, `catalog.changed`.
- Errors: `400 validation_error` (manifest with `main`, provider ids not `<pluginId>` / `<pluginId>-<suffix>`,
  icon mismatch, credentials for an undeclared provider); `403 forbidden` (reserved id); `409 conflict`
  (`reason: 'exists'`: the plugin id, or a provider / MCP server id already used by another plugin).

**`POST /plugins/drafts/test`** — `pluginDrafts.test`
- Body `DraftTestRequest`. Builds a temporary provider from the draft (nothing stored) and runs `action`
  (15 s timeout).
- Response `200 DraftTestResult` (`ok: false` + `error` on failure, not an HTTP error).

**`PUT /plugins/:id/manifest`** — `pluginDrafts.updateManifest` · **fresh** when a stdio MCP server is declared or changed
- Params `{ id: PluginId }`. Body `PluginManifestUpdate`. Replaces `plugin.json` of a declarative editable plugin
  and reloads it (hot reload on save). A manifest that declares or changes a stdio MCP server requires fresh auth
  and re-pins the trust hash.
- Response `200 PluginDetail`.
- Errors: `404 not_found`; `403 forbidden` (not editable, builtin, or a code plugin: use the files API);
  `400 validation_error` (id changed, invalid manifest).

### 5.18 `plugin-files.ts`

Path rules for `*` (`params.path`): relative POSIX path, 1..256 chars, segments of `[A-Za-z0-9._-]`, at most 8
segments; no leading `/`, no `.` or `..` segments, no backslashes, no NUL; resolved with `realpath` inside the
plugin dir. Violations -> `400 validation_error`. Files are text only (valid UTF-8, no NUL) and at most 1 MB.

Additional guards (all `400 validation_error`):

- `.git` and `node_modules` are never listed or opened, even for reading.
- Hidden files and folders (a segment starting with `.`) are listed with `editable: false` and cannot be created,
  changed or deleted, so a stolen session cannot plant `.git/hooks` or editor tasks in a linked folder.
- Symbolic links are neither listed nor followed; a path that differs only in letter case from an existing entry
  (`PLUGIN.JSON`) is refused.

**`POST /plugins/scaffold`** — `pluginFiles.scaffold` · **fresh**
- Body `ScaffoldRequest`. Creates `data/plugins/<id>/` from the template (`plugin.json` + `index.mjs` or
  `index.ts`), `source: 'created'`, trusted (hash pinned), enabled and loaded.
- Response `201 PluginDetail`.
- Errors: `403 forbidden` (reserved id); `409 conflict` (`reason: 'exists'`).

**`GET /plugins/:id/files`** — `pluginFiles.list`
- Params `{ id: PluginId }`.
- Response `200 ListResponse<PluginFileEntry>`: recursive (at most 8 levels), directories first then files, sorted
  by path; skips `node_modules`, `.git`, symbolic links and temporary files of atomic writes (build output lives in
  `data/cache/plugins/<id>/`, outside the plugin dir); at most 2000 entries.
- Errors: `404 not_found`; `403 forbidden` (builtin).

**`GET /plugins/:id/files/*`** — `pluginFiles.read`
- Params `PluginFileParams`.
- Response `200 PluginFileContent`.
- Errors: `404 not_found`; `400 validation_error` (bad path, binary file); `413 payload_too_large` (> 1 MB);
  `403 forbidden` (builtin).

**`PUT /plugins/:id/files/*`** — `pluginFiles.write` · **fresh** for plugins that run code
- Params `PluginFileParams`. Body `PluginFileWrite` (creates missing parent directories).
- Writes are atomic and never trigger the file watcher. `plugin.json` must stay a valid manifest with the same id.
  Declarative plugins reload when `plugin.json` is written; code changes take effect on `POST /plugins/:id/build`.
- Fresh auth (ADR-017): writing a file of a plugin that runs code (a code plugin or a stdio MCP server), or a
  `plugin.json` that would make it run code, requires fresh auth when a password is set.
- Trust (ADR-017): a write to a plugin with source `created` re-pins its trust hash only when the plugin was trusted
  before the write (or needed no trust); a plugin whose files had already changed outside the editor stays
  `untrusted` (a `warn` entry in its log) until it is trusted explicitly. For source `copy` a change of the hashed
  files (`plugin.json`, the entry) makes a code or stdio-MCP plugin `untrusted` until it is trusted again; `link`
  plugins are pinned by path.
- Response `200 PluginFileEntry`.
- Errors: `404 not_found` (plugin); `403 forbidden` (not editable); `409 conflict` (`reason: 'stale'`);
  `400 validation_error`; `413 payload_too_large`.

**`DELETE /plugins/:id/files/*`** — `pluginFiles.remove` · **fresh** for plugins that run code
- Params `PluginFileParams`. Deletes one file (not a folder); directories left empty are removed. Rename in the
  editor = write the new path, then delete the old one. `plugin.json` and the files it references (the `main` entry
  and a file `icon`) cannot be deleted.
- Fresh auth and trust: as for writes (plugins that run code need fresh auth; a trusted `created` plugin is
  re-pinned automatically).
- Response `204`.
- Errors: `404 not_found` (plugin or file); `403 forbidden` (not editable, builtin); `400 validation_error` (bad
  path, a folder, `plugin.json` or a file it references).

**`POST /plugins/:id/build`** — `pluginFiles.build` · **fresh**
- Params `{ id: PluginId }`. Body `PluginBuildBody`.
- Compiles/checks the entry with esbuild (`.ts`: bundled into `data/cache/plugins/<id>/<sha256>.mjs` with the SDK
  aliased to the host shim; `.mjs`/`.js`: syntax and import check), collects diagnostics, and when there are no
  errors re-pins the trust hash of a `created` plugin (the hash of the files that were built) and (if `reload`)
  reloads the plugin; a failed reload is added as an error diagnostic. Build log lines are written to the plugin log
  (`plugin.log` events).
- Response `200 BuildResult` (a failed build is `ok: false` with diagnostics, not an HTTP error).
- Errors: `404 not_found`; `403 forbidden` (not editable, builtin, declarative plugin).

### 5.19 `data.ts`

Bulk data (ADR-024, formats in section 4.16). Only one import or delete-all runs at a time; a second one gets
`409 conflict` (`reason: 'busy'`). No new event types: the chat events of section 7 report the changes.

**`GET /data`** — `data.summary`
- Response `200 DataSummary` (what a backup contains and what delete-all removes).

**`GET /data/export?files=true|false&settings=true|false`** — `data.export` · response `'binary'`
- Query `DataExportQuery` (both default `true`).
- Response `200 application/zip`, streamed while it is downloaded, with
  `Content-Disposition: attachment; filename="harness-forge-backup-<yyyy-mm-dd>.zip"` and `Cache-Control: no-store`;
  the layout of section 4.16 (`manifest.json` last). A `HEAD` request gets the headers only (no zip is built).
- Errors: `413 payload_too_large` when the zip would exceed 3.5 GB or 65,000 entries (no zip64; the message suggests
  exporting with `files=false`).

**`POST /data/import`** — `data.import` · multipart
- Body `multipart/form-data`: the upload in part `file` + `DataImportForm` fields; limit 256 MB
  (`LIMITS.backupImportBytes`). The content decides the kind: `PK` = a backup zip, `{` = one chat JSON
  (`ChatExportAny`, version 1 or 2).
- Backups are read lazily with the plugin installer's zip guards (path traversal, symbolic links, duplicate names,
  at most 50,000 entries, declared and actual sizes, CRC); each chat entry is at most 64 MB and each file blob at most
  20 MB before it is inflated; a manifest of a newer `version` is refused; unknown entries become `warnings`.
- Each chat is imported atomically, one failure never stops the others (`status: 'failed'` + `error`): `skip` keeps
  an existing chat with the same id, so running the same import again changes nothing; `copy` imports it under new
  chat and message ids with " (imported)" appended to the title. Title, pinned, archived, dates and every message
  version (the tree and the active leaf) are restored. Attachments are re-hashed against `files/index.json` and
  re-checked (type), reused when the same content is stored, and the `/api/files/<id>` URLs of the parts are
  rewritten to the stored ids; a referenced file absent from the backup counts in `filesMissing`.
- `restoreSettings=true` applies the known keys of `settings.json`, each validated on its own (invalid keys become
  warnings); secrets and the password are never part of a backup.
- Response `200 DataImportResult`. Emits `chat.created` for every imported or copied chat.
- Errors: `400 validation_error` (neither a zip nor a chat JSON, a zip guard violation, a missing or newer manifest,
  an invalid chat JSON); `409 conflict` (`reason: 'busy'`); `413 payload_too_large`.

**`POST /data/delete`** — `data.deleteAll` · **fresh**
- Body `DataDeleteBody` (`confirm` must be the literal `DELETE`).
- Stops every run (runs still preparing included), then deletes every chat with its messages and share links;
  `usage: true` also deletes the usage rows (else they are kept with `chat_id = NULL`); `files: true` also deletes
  every uploaded file (rows and blobs). Settings, providers, credentials, plugins and MCP servers are kept.
- Response `200 DataDeleteResult`. Emits `chat.deleted` for every deleted chat.
- Errors: `403 forbidden` (fresh auth missing, `action: 'login'`); `409 conflict` (`reason: 'busy'`).

### 5.20 `shares.ts`

Read-only share links (ADR-025, DTOs in section 4.17). The owner routes need a session; creating and changing a link
also need fresh auth (a link turns brief session access into lasting remote access), revoking does not. The two
`/share/:token` routes are **public** and read only the stored snapshot (never live messages; they write nothing, no
view counters); the chat must still exist. The token is never stored: the owner can copy `path` again, revoking
deletes the row, a new master key invalidates every link. The passwordless host guard is unchanged, so exposing links
requires `HF_PASSWORD`. Every response carries `X-Robots-Tag: noindex, nofollow`; tokens are masked in logs. Share
actions emit no server event (the owner UI refetches).

**`GET /shares?chatId=`** — `shares.list`
- Query `SharesQuery`.
- Response `200 ListResponse<ShareSummary>`, newest first.

**`POST /shares`** — `shares.create` · **fresh**
- Body `ShareCreate`. Snapshots the chat's active path through the allowlist sanitizer (section 4.17).
- Response `201 ShareSummary`.
- Errors: `404 not_found` (unknown chat); `400 validation_error` (`expiresAt` not in the future or more than 365 days
  ahead, or the chat already has `LIMITS.sharesPerChatMax` (20) links); `413 payload_too_large` (the snapshot exceeds
  10 MB, `details.limitBytes`); `403 forbidden` (fresh auth missing, `action: 'login'`).

**`PATCH /shares/:id`** — `shares.update` · **fresh**
- Params `{ id: ShareId }`. Body `ShareUpdate`. `refresh: true` re-snapshots the chat's current active path; changed
  `options` apply to the share page at once; the token and `path` never change.
- Response `200 ShareSummary`.
- Errors: `404 not_found` (unknown share); `400 validation_error` (`expiresAt`); `413 payload_too_large` (refreshed
  snapshot); `403 forbidden` (fresh auth missing, `action: 'login'`).

**`DELETE /shares/:id`** — `shares.remove`
- Params `{ id: ShareId }`. Revokes the link: the row is deleted and the token stops working at once.
- Response `204`.
- Errors: `404 not_found`.

**`GET /share/:token`** — `shares.view` · public
- Params `SharePublicParams`.
- Response `200 ShareView` (file URLs rewritten to `/api/share/<token>/files/<fileId>`), `Cache-Control: no-store`.
- Errors: `404 not_found`, the same response for every failure: a malformed, unknown, bad-MAC, revoked or expired
  token, or a deleted chat (never `400`); `429 rate_limited` (`retryAfterMs`, `Retry-After`): 60 views per minute and
  20 invalid tokens per 10 minutes per client address (ADR-026 for proxies), 6000 requests per minute in total.

**`GET /share/:token/files/:fileId`** — `shares.file` · public · response `'binary'`
- Params `ShareFileParams`. Serves only the files of the share's snapshot.
- Response `200` bytes with the headers of `GET /files/:id` (type, `nosniff`, sandboxing CSP, `inline` only for raster
  images and PDF) except `Cache-Control: no-store` and no `ETag`.
- Errors: the same `404 not_found` (also for a file that is not part of the share); `429 rate_limited` (600 requests
  per minute per client address).

## 6. Chat stream protocol

`POST /api/chat` returns an **AI SDK v7 UI message stream** built with
`createUIMessageStreamResponse({ stream: toUIMessageStream({ stream: result.stream, ... }), consumeSseStream })`.
Verify every AI SDK name against the installed `node_modules/ai` types before implementing.

### 6.1 Client setup (reference)

```ts
import { DefaultChatTransport, lastAssistantMessageIsCompleteWithApprovalResponses } from 'ai'
import { useChat } from '@ai-sdk/vue'
import { createMessageId, harnessDataSchemas, messageMetadataSchema,
  type ChatRequestBody, type HarnessUIMessage } from '@harness-forge/shared'

const chat = useChat<HarnessUIMessage>({
  id: chatId,                                   // uuidv7 (createChatId() for a new chat)
  messages: detail?.messages ?? [],             // ChatDetail.messages
  throttle: 50,                                 // optional: batch reactive updates (ms)
  generateId: createMessageId,                  // user message ids: msg_ + 16 chars
  messageMetadataSchema,
  dataPartSchemas: harnessDataSchemas,
  sendAutomaticallyWhen: lastAssistantMessageIsCompleteWithApprovalResponses,
  transport: new DefaultChatTransport({
    api: '/api/chat',
    prepareSendMessagesRequest: ({ id, messages, trigger, messageId }) => {
      const message = messages[messages.length - 1]!
      const target = trigger === 'regenerate-message'
        ? { messageId }                                    // the reply to regenerate (undefined = active leaf)
        : message.role === 'user'
          ? { parentId: messages.at(-2)?.id ?? null }      // new or edited user message: its parent
          : {}                                             // approval continuation: neither
      return {
        body: {
          chatId: id, message, trigger, ...target,
          modelRef, reasoningEffort, toolMode,             // current composer state
        } satisfies ChatRequestBody,
      }
    },
  }),
})
// resume: @ai-sdk/vue 4 has no `resume` option (React only); on mount, when the chat has an active run
// (ChatSummary.running, or a run.started event), call:
void chat.resumeStream()                        // GET /api/chat/:id/stream, 204 -> nothing to do
// approvals: chat.addToolApprovalResponse({ id: part.approval.id, approved, reason? })
// stop:      await client.chat.stop({ params: { id } }); chat.stop()
```

### 6.2 What `message` contains

The messages of a chat form a tree (ADR-023): editing a message or regenerating a reply adds a sibling **version**;
nothing is deleted. `ChatDetail.messages` is the active path, `ChatDetail.branches` lists the versions, and
`POST /chats/:id/branch` switches between them.

| User action | `useChat` call | `trigger` | `parentId` / `messageId` | `message` (last UI message) | Server behavior |
|---|---|---|---|---|---|
| Send | `sendMessage({ text, files })` | `submit-message` | `parentId` = the previous message (`null` for a first message; omitted = the active leaf) | new user message | stored under `parentId` and made the active leaf; pending approvals on that path resolved as denied (`superseded`, `data-notice` `approvals-superseded`) |
| Edit | the local messages are cut before the edited one, then `sendMessage({ text, files })` (a new id) | `submit-message` | `parentId` = the edited message's parent | new user message | a sibling version of the edited message; the old version and its later messages stay stored (switch back with `POST /chats/:id/branch`) |
| Regenerate | `regenerate({ messageId? })` | `regenerate-message` | `messageId` = the reply to regenerate, or a user message to answer (default: the active leaf) | the user message it answers | a new reply as a sibling of the old one (the old reply is kept); the answered user message is the active leaf until the new reply is stored |
| Approval continuation | automatic (`sendAutomaticallyWhen`) | `submit-message` | neither | the active leaf assistant message with `approval-responded` parts | merge only approval decisions by `approval.id`; continue the same assistant message |

Rejected before streaming: a user message sent with `messageId` (`400`, in-place edits were removed), `parentId` on a
regenerate or a continuation (`400`), a regenerate target not answered by a user message (`400`), an unknown
`parentId` or `messageId` (`404`: the web refetches the chat, its local path is stale), a continuation that is not the
active leaf (`404`), and a user message id that is already stored (`409`, `reason: 'exists'`). The web never sends
the id of a user message whose request failed with an HTTP error (the server stored nothing).

User text parts: plain text (slash commands are expanded server-side, see ARCHITECTURE.md 6.1). File parts:
`{ type: 'file', mediaType, filename, url: '/api/files/<id>' }` from `POST /files`; the server loads the bytes
only for models with `vision` (images) or `pdf` capability, otherwise the part is kept for display and a
`data-notice` explains it was not sent.

### 6.3 Response

- Server options: `toUIMessageStream({ stream: result.stream, originalMessages, generateMessageId: createMessageId,
  sendReasoning: true, sendSources: true, messageMetadata, onError, onEnd })` (`sendSources` defaults to false in
  v7; the web renders sources, so it must be true). Headers come from `UI_MESSAGE_STREAM_HEADERS`.
- Status `200`, headers `Content-Type: text/event-stream`, `x-vercel-ai-ui-message-stream: v1`,
  `Cache-Control: no-cache`, `X-Accel-Buffering: no`, `X-Request-Id`.
- Body: SSE events `data: <UIMessageChunk JSON>\n\n`, terminated by `data: [DONE]\n\n`.
- Chunk types used (v7): `start` (with `messageId`, `messageMetadata`), `start-step`, `finish-step`,
  `text-start` / `text-delta` / `text-end`, `reasoning-start` / `reasoning-delta` / `reasoning-end`,
  `tool-input-start` / `tool-input-delta` / `tool-input-available` / `tool-input-error`, `tool-approval-request`,
  `tool-output-available` / `tool-output-error` / `tool-output-denied`, `source-url`, `source-document`, `file`,
  `data-notice`, `message-metadata`, `error`, `abort`, `finish` (with `messageMetadata`). The web consumes them
  only through `useChat`; it never parses chunks itself.

### 6.4 UI message parts the web renders

| Part `type` | States / fields | Rendering (details in UI.md) |
|---|---|---|
| `text` | `state: 'streaming' \| 'done'` | `Markdown.vue` (HTML escaped); final render when `done` |
| `reasoning` | `state: 'streaming' \| 'done'` | "Thinking... Ns" row, then "Thought for Ns", collapsed unless `showThinking` |
| `reasoning-file` | `mediaType`, `url` | file chip inside the reasoning block |
| `tool-<name>` | static tools (`ctx.ai.tool` / builtin tools) | tool row, see states below |
| `dynamic-tool` | `toolName`; runtime tools (MCP tools) | same tool row (+ MCP server badge) |
| `file` | `mediaType`, `filename?`, `url` | image thumbnail (`image/*`) or file chip |
| `source-url` | `sourceId`, `url`, `title?` | grouped "N sources" row |
| `source-document` | `sourceId`, `mediaType`, `title`, `filename?` | grouped "N sources" row |
| `step-start` | - | step boundary (no visual, used by the approval helper) |
| `data-notice` | `NoticeData` | muted notice row |
| other `data-*`, `custom` | - | ignored |

Tool part states (`tool-<name>` and `dynamic-tool`):

| `state` | Meaning | Row |
|---|---|---|
| `input-streaming` | arguments streaming (`input` partial) | spinner |
| `input-available` | arguments complete, executing | spinner |
| `approval-requested` | waits for the user (`approval.id`) | amber, `AiConfirmation` card: Deny / Allow + "Always allow {tool}" checkbox |
| `approval-responded` | decision sent, continuation pending (`approval.approved`) | spinner (allowed) or "Denied" |
| `output-available` | `output` (may be `preliminary: true`) | check mark, expandable input/output (4 KB cap in UI) |
| `output-error` | `errorText` | cross, error text |
| `output-denied` | `approval.approved === false` (`approval.reason`, `approval.isAutomatic`) | "Denied" |

### 6.5 Metadata and errors

- `start` carries `messageMetadata: { modelRef, startedAt }`; `finish` carries `{ finishedAt, durationMs,
  reasoningMs?, usage, costUsd?, finishReason }`. Both merge into `message.metadata` (`MessageMetadata`). An
  aborted message is persisted with `aborted: true`; the live client learns it from the `abort` chunk and
  `run.finished`.
- **Before streaming** (validation, `provider_not_configured`, `conflict`, `not_found`): normal JSON error
  response; `DefaultChatTransport` throws an `APICallError` (`statusCode`, `responseBody` = envelope JSON,
  `message` = the same text) that `useChat` exposes as `chat.error`.
- **During streaming**: `onError` maps the error (section 2.3) and returns the envelope JSON (`JSON.stringify(e.toJSON())`), sent as
  `{ "type": "error", "errorText": "{\"error\":{\"code\":\"auth_invalid\",...}}" }`; the same `HarnessErrorInit` is
  persisted in `metadata.error`. Tool execution errors do not end the stream: they become `output-error` parts.
- The web always calls `HarnessError.from(chat.error)` (and reads `metadata.error` of stored messages) and maps
  `code` / `action` to UX: `configure-provider` -> "Open settings", `refresh-models` -> refresh, `retry` -> Retry
  (`regenerate()`), `login` -> login.

### 6.6 Resume and stop

- `GET /api/chat/:id/stream`: `204` when no run is active; otherwise the same stream format, replayed from the
  first chunk of the active run, then live chunks. At most one run per chat, so resume needs no run id. While a
  run is active, `GET /chats/:id` returns the path to the leaf committed when the run started (the new or answered
  user message, or the continued assistant message) and excludes the in-flight reply (an approval continuation
  shows the pre-continuation message), so the replay is applied exactly once on top of it; the web refetches the
  chat on `run.finished` unless it is streaming it itself (ARCHITECTURE.md 6.3). `POST /chats/:id/branch` is
  refused with `409 conflict` (`reason: 'run-active'`) while a run holds the chat.
- `POST /api/chat/:id/stop`: aborts the run (`abort` chunk to every reader), persists the partial message with
  `aborted: true`; returns `{ stopped }`. The web calls it before `chat.stop()`; a client abort alone only
  disconnects (the run continues and stays resumable).
- A second `POST /api/chat` for a chat with an active run gets `409 conflict` (`reason: 'run-active'`).

### 6.7 Approvals

- Approval decisions come from the server-side approval function (ARCHITECTURE.md 6.2) passed as
  `streamText({ toolApproval })`; `experimental_toolApprovalSecret` (HKDF `approval` subkey) signs approval
  requests so a response is valid only for the exact tool call and input.
- The continuation request carries the whole last assistant message, but the server merges only
  `approval.approved` / `approval.reason` per `approval.id` into the stored copy; any other client change is
  ignored.
- Allow with "Always allow {tool}" checked = `PATCH /api/tools/:name` `{ override: 'allow' }` +
  `addToolApprovalResponse(...approved: true)`.
- Approvals on other versions of a chat stay pending: switching back to such a version sets `pendingApproval` again,
  and the approval card is live because the continuation targets the active leaf.

## 7. Server events (`GET /api/events`)

- Session required. Response `200` with `Content-Type: text/event-stream`, `Cache-Control: no-cache`,
  `Connection: keep-alive`, `X-Accel-Buffering: no`. The web opens one `EventSource('/api/events')` per tab
  (`plugins/events.client.ts`).
- Wire format: first `retry: 3000`, then per event:

  ```
  id: 42
  event: chat.updated
  data: {"type":"chat.updated","data":{...ChatSummary},"at":1759000000000}

  ```

  `id` is a per-process increasing integer; `event` equals `type`; `data` is the full `ServerEvent` JSON.
- Heartbeat: a comment line `: ping` every **25 s**. Each heartbeat re-checks the session: the stream ends when it
  is no longer valid (password changed, logged out, expired). Shutdown also ends every stream.
- No replay: `Last-Event-ID` is ignored. After a reconnect (`EventSource` `open` following an `error`) the web
  refetches its stores. A slow connection whose queue exceeds 256 events is closed by the server.

| Event | Emitted when | `data` | Web reaction |
|---|---|---|---|
| `chat.created` | `POST /chats`, the first `POST /chat` for a new chat id, or `POST /data/import` (one per imported or copied chat) | `ChatSummary` | chats store: insert |
| `chat.updated` | title generated or renamed, pin/archive/model/settings change, a message persisted, a branch switch (`POST /chats/:id/branch`) | `ChatSummary` | chats store: patch and re-sort |
| `chat.deleted` | `DELETE /chats/:id`, or `POST /data/delete` (one per deleted chat) | `{ id }` | chats store: remove; leave `/chat/:id` if open |
| `run.started` | a run acquired the chat | `RunStartedData` | running dot |
| `run.finished` | run completed, aborted or failed | `RunFinishedData` | clear running; amber dot when `awaitingApproval` |
| `provider.changed` | credentials set/cleared, enable/disable, validation result, provider (un)registered | `{ id, provider }` | providers store: patch or remove |
| `catalog.changed` | listing refresh, prefs or custom model change, plugin (un)load, models.dev refresh | `{ providerId }` | models store: refetch `GET /models` |
| `plugin.changed` | install, uninstall, enable, disable, reload, trust, build, state change, MCP connection change | `{ id, plugin }` | plugins store: patch or remove; MCP panel refetches |
| `plugin.log` | new plugin log entry (logger, guard failure, build output) | `{ pluginId, entry }` | Logs tab / build panel append |

Phase 5 adds no event types: bulk import and delete-all report every chat through `chat.created` / `chat.deleted`,
a branch switch through `chat.updated`; share link actions emit nothing (the owner UI refetches).
