# HTTP API

The binding contract between `apps/web`, `apps/server` and `packages/shared`. `packages/shared` implements every
schema, route and helper named here **verbatim**; the server validates requests with these schemas
(`@hono/zod-validator`) and contract tests validate its responses against them. Names come from
[DECISIONS.md](./DECISIONS.md) (contract seed); architecture and flows are in [ARCHITECTURE.md](./ARCHITECTURE.md).

Contents: 1 Conventions · 2 Errors · 3 `packages/shared` naming contract · 4 Schemas · 5 Endpoints ·
6 Chat stream protocol · 7 Server events · 8 Route key index

## 1. Conventions

| Topic | Rule |
|---|---|
| Base path | Everything under `/api` (paths below omit it). Unknown `/api/*` paths return `404 not_found` JSON. |
| Format | JSON (`application/json; charset=utf-8`) request and response bodies unless a route says otherwise (SSE, UI message stream, multipart, binary). Request bodies are validated with zod; unknown keys are rejected (`.strict()`) except inside UI messages. A non-empty body sent to a JSON route must be `application/json` (or `+json`); routes with a multipart `form` also accept `multipart/form-data`; anything else -> `400 validation_error` (no form-encoded CSRF). |
| Auth | Session cookie `hf_session` (HttpOnly, SameSite=Strict). When a password is configured, every route except the public ones (marked **public**) returns `401 unauthorized` without a valid session. Without a password every request is authenticated. |
| CSRF | Origin check on every state-changing request (not `GET` / `HEAD` / `OPTIONS`; ARCHITECTURE.md 10.2): an `Origin` other than the server origin (the request's scheme + `Host`), or, without `Origin`, a `Sec-Fetch-Site` other than `same-origin` / `none` -> `403 forbidden`. By design a request with neither header (a non-browser client such as curl, which cannot ride on the user's cookie) passes. |
| Reverse proxies | ADR-026, ARCHITECTURE.md 10.6. `X-Forwarded-For` counts only when `HF_TRUST_PROXY` lists the TCP peer: the client address (the key of the login and share rate limits) is then the first entry that is not a listed proxy, read from the right; otherwise it is the TCP peer. `X-Forwarded-Proto` (HTTPS: `Secure` cookie, HSTS, the scheme of the Origin check) counts only from a listed proxy when `HF_TRUST_PROXY` is set, from any peer when it is unset (v1). `X-Forwarded-Host` and `Forwarded` are never read. |
| Fresh auth | ADR-017. Sensitive routes (marked **fresh**) additionally require a login within the last 10 minutes when a password is set, else `403 forbidden` with `action: 'login'`. The proof is the session itself (`authAt`, `AuthStatus.freshUntil`): the web asks for the password, calls `POST /auth/login` and retries. |
| Success codes | `200` with a body; `201` for creations (`POST` that creates a resource); `204` for no body. |
| Errors | Every non-2xx response is a `HarnessErrorEnvelope` (section 2). |
| Timestamps | Integers, Unix epoch **milliseconds**. |
| Booleans in query strings | `true` / `false` (also `1` / `0`); coerced by the query schemas. |
| Pagination | Cursor based: `?cursor=<opaque>&limit=<1..100, default 50>` -> `{ items, nextCursor }`; `nextCursor` is `null` on the last page. Cursors are opaque base64url strings; an invalid cursor -> `400 validation_error`. Non-paginated lists return `{ items }`. |
| Ids | Chat: uuidv7 (lowercase, generated by the client with `createChatId()`). Message: `msg_` + 16 chars `[0-9A-Za-z]` (`createMessageId()`; assistant ids generated by the server, user ids by the client). File: `file_` + 16 chars. Share: `shr_` + 16 chars; share token: the 16-char share id suffix + 22 base64url chars (ADR-025). Project: `prj_` + 16 chars (`createProjectId()`, ADR-031). Shell rule: `srl_` + 16 chars (ADR-038). Change batch (one revert, rewind or undo): `wcb_` + 16 chars (ADR-036). Plugin: `^[a-z0-9](?:[a-z0-9-]{0,38}[a-z0-9])?$`. Tool: `^[a-zA-Z0-9_-]{1,64}$`. Command: `^[a-z][a-z0-9-]{0,31}$`. MCP server: `^[a-z0-9](?:[a-z0-9-]{0,30}[a-z0-9])?$`. |
| Model ref | `providerId:modelId`, split on the **first** `:` (`ollama:llama3:8b`, `openrouter:anthropic/claude-sonnet-5`). Model refs travel only in bodies and query strings, **never in URL paths**; when a model must be addressed, `providerId` and `modelId` are separate fields. |
| Path params | URL-encoded by the client; `*` rest paths (plugin files) keep `/` separators and encode each segment. |
| Caching | JSON responses: `Cache-Control: no-store`. Icons and hashed assets: see their routes. |
| Request id | `X-Request-Id` response header on every response (ARCHITECTURE.md 12). |

## 2. Errors

### 2.1 Envelope and `HarnessError`

```ts
// Plain JSON error object: DTO fields (lastError, metadata.error, ...), the envelope content, and the return
// type of a provider's mapError() (plugin-sdk re-exports it)
type HarnessErrorInit = {                   // harnessErrorInitSchema
  code: HarnessErrorCode
  message: string            // human readable, English, safe to show; never contains secrets
  status?: number            // HTTP status reported by an UPSTREAM service (provider, MCP server, npm registry,
                             // install URL) when the error came from one, e.g. 401 -> UI badge "Error 401";
                             // the HTTP status of OUR response is derived from `code` (table 2.2)
  providerId?: string        // provider involved, when any
  retryAfterMs?: number      // for rate_limited (also sent as the Retry-After header, in seconds, rounded up)
  action?: HarnessErrorAction  // UI hint
  details?: unknown          // code-specific, see 2.3
}

// HTTP body of every non-2xx response, and the JSON inside in-stream `errorText` (section 6.5)
type HarnessErrorEnvelope = { error: HarnessErrorInit }   // harnessErrorEnvelopeSchema

// Throwable used by the server (thrown by services/routes, rendered by the error handler) and by the client
// (thrown by createApiClient on non-2xx)
class HarnessError extends Error implements HarnessErrorInit {
  constructor(init: HarnessErrorInit)
  readonly code: HarnessErrorCode           // + every other HarnessErrorInit field
  readonly requestId?: string               // client side: X-Request-Id of the failed response
  get httpStatus(): number                  // errorStatusByCode[code]
  toJSON(): HarnessErrorEnvelope
  static from(input: unknown): HarnessError // HarnessError -> itself; HarnessErrorInit or envelope object or
                                            // envelope JSON string; an Error whose `message` (or `responseBody`,
                                            // for the AI SDK APICallError) is envelope JSON; anything else ->
                                            // code 'internal_error' with a generic message
}
```

### 2.2 Codes, HTTP status, action

The HTTP status of an error response is determined by `code` (`errorStatusByCode` in `shared`). The web redirects
to `/login` only on `code === 'unauthorized'`, never on the HTTP status alone.

| `code` | HTTP | Typical `action` | Meaning |
|---|---|---|---|
| `validation_error` | 400 | - | Request failed zod validation or a semantic check (`details.issues`). |
| `unauthorized` | 401 | `login` | No valid session (or wrong password on `POST /auth/login`). |
| `forbidden` | 403 | `login` when fresh auth is missing | Origin check failed, fresh auth missing, operation not allowed for this resource (builtin plugin, read-only source). |
| `not_found` | 404 | - | Unknown route, chat, message, plugin, provider, file, tool, MCP server, icon, share link, project, shell rule or change batch, a file the chat never changed, or a missing project folder. Every failure of the public share routes is the same 404 (section 5.20). |
| `conflict` | 409 | - | State conflict: a run is active for the chat (or for a chat of the project, also during a rewind, revert or undo), id already exists (also a project for the folder, the new folder, or a shell rule), stale file `baseEtag` (or a revert's `expectedSha`), password managed by `HF_PASSWORD`, another maintenance operation (import, delete-all, key rotation, file cleanup) is running, a chat request arrives during a key rotation, the message to delete is its only version, the master key comes from `HF_MASTER_KEY` or fails the key check. |
| `payload_too_large` | 413 | - | Body, upload, zip, backup, recording, share snapshot or file over the limit (`details.limitBytes`; a backup with too many entries: `details.limitEntries`). |
| `provider_not_configured` | 400 | `configure-provider` | Provider unknown/disabled or required credentials missing, wherever a model ref is resolved (chat, media routes, `ctx.ai`, `ctx.models.resolve`, `ctx.images`, `generate_image`; an unknown provider since Phase 7). Returned before any streaming. Routes that address a provider by id (`/providers/:id/...`, `GET /models?providerId=`, model prefs, custom models) answer `404 not_found` for an unknown one. |
| `auth_invalid` | 502 | `configure-provider` | Provider rejected the credentials (upstream 401/403). |
| `rate_limited` | 429 | `retry` | Upstream rate limit, login rate limit or share link rate limit; `retryAfterMs` when known. |
| `model_not_found` | 404 | `refresh-models` | Provider does not know the model (upstream 404). |
| `context_overflow` | 400 | - | Prompt exceeds the model context window even after trimming. |
| `provider_unreachable` | 502 | `retry` | Network failure reaching an upstream service: provider, MCP server, npm registry, install URL (ECONNREFUSED, ENOTFOUND, timeout). |
| `provider_error` | 502 | `retry` | Any other upstream error (provider, MCP server, npm registry, install URL). |
| `plugin_error` | 500 | - | Plugin code threw, timed out, or failed to load/build (`details.pluginId`). |
| `internal_error` | 500 | `retry` | Unexpected server error (`details.requestId`). Message is generic; details are logged. |
| `not_implemented` | 501 | - | Route and service stubs between a contract wave and the feature wave that implements them (the Phase 0 skeleton; in Phase 6 `audio.transcribe`, `audio.speech` and `chats.deleteMessage` from P6-0a until P6-A; in Phase 7 the five `projects` routes, `keys.get`, `keys.rotate`, `data.cleanupPreview` and `data.cleanup` from P7-0a until P7-A; in Phase 8 the seven `changes` routes and the three `shellRules` routes from P8-0a until P8-A). No route of a release answers it. |

`HarnessErrorAction` = `configure-provider | refresh-models | login | retry`.

### 2.3 `details` by code

| Code | `details` shape |
|---|---|
| `validation_error` | `{ issues: Array<{ path: Array<string \| number>; message: string; code: string }> }` (zod issues, flattened) |
| `conflict` | `{ reason: 'run-active' \| 'exists' \| 'stale' \| 'disabled' \| 'env-password' \| 'insecure-bind' \| 'busy' \| 'only-version' \| 'env-key' \| 'key-mismatch', chatId?: string }` (`run-active`: a run holds the chat, or its active leaf moved during a version switch or delete, section 5.9, or a chat of the project runs while the project is deleted, or the chat runs while it is moved, sections 5.9 and 5.22, or a chat of the project runs during a rewind, revert or undo, section 5.24; `exists`: a chat or message id is already used, a project already uses the folder, the new folder exists, section 5.22, or the shell rule already exists, section 5.25; `stale`: a plugin file or package changed since it was read or reviewed, or a chat request was stopped before its history was stored, section 5.10, or the file to revert changed since the client read it (`expectedSha`), section 5.24; `busy`: another maintenance operation (import, delete-all, key rotation, file cleanup) is running, sections 5.19 and 5.23, or a chat request arrives while a key rotation runs, section 5.10; `only-version`: the message to delete has no other version, section 5.9; `env-key`: the master key comes from `HF_MASTER_KEY` and is rotated offline, section 5.23; `key-mismatch`: the master key fails the stored key check, section 5.23) |
| `payload_too_large` | `{ limitBytes: number }`, or `{ limitEntries: number }` when `GET /data/export` refuses a backup for its entry count (section 5.19) |
| `plugin_error` | `{ pluginId: string; phase?: 'load' \| 'setup' \| 'dispose' \| 'hook' \| 'tool' \| 'build' \| 'install' }` |
| `internal_error` | `{ requestId: string }` |
| others | omitted, or `{ upstream?: string }` (a short, redacted upstream message) |

Provider error mapping (chat pipeline and provider calls): `provider.mapError(err)` first; then upstream 401/403 ->
`auth_invalid`; 429 -> `rate_limited`; 404 -> `model_not_found`; context-length errors -> `context_overflow`;
`ECONNREFUSED` / `ENOTFOUND` / `ETIMEDOUT` / fetch timeout -> `provider_unreachable`; everything else ->
`provider_error`. `providerId` and `status` are set when known.

## 3. `packages/shared` naming contract

C1+C2 (one agent, both contract packages) implements exactly these exports (file layout inside
`packages/shared/src` is free; everything is re-exported from the package root).

### 3.1 Schemas and types

- Every DTO in section 4 is a zod v4 schema named `<camelCase>Schema` with an inferred PascalCase type of the same
  base name: `export const chatSummarySchema = z.object({...})` +
  `export type ChatSummary = z.infer<typeof chatSummarySchema>`.
- Enums: `<camelCase>Schema = z.enum([...])` + type (`toolModeSchema` / `ToolMode`).
- Generic helpers: `listResponseSchema(item)` -> `{ items: T[] }`, `cursorPageSchema(item)` -> `{ items: T[];
  nextCursor: string | null }`, types `ListResponse<T>`, `CursorPage<T>`.
- Request schemas that are not DTOs use the suffixes `Query`, `Params`, `Body`/`Update`/`Input` as listed in
  section 4 (`chatsQuerySchema`, `chatUpdateSchema`, `customModelInputSchema`, ...).

### 3.2 Package layering and plugin data shapes

`@harness-forge/plugin-sdk` depends on `@harness-forge/shared` (`workspace:*`); `shared` never imports
`plugin-sdk` (no cycle). Therefore `shared` owns every JSON shape that crosses the HTTP boundary, including the
plugin **data** shapes that API DTOs embed (shapes defined in [PLUGINS.md](./PLUGINS.md), plan Appendix A).
`plugin-sdk` re-exports them unchanged and adds the runtime contract (`PluginContext`, `ProviderDefinition`,
`ToolDefinition`, `CommandDefinition`, `HookMap`, `PluginModule`, `definePlugin`, `PLUGIN_API_VERSION`,
`settingsValuesSchema()`, ...). Plugin authors keep importing everything from `@harness-forge/plugin-sdk`.

| Type (name fixed) | Schema in `shared`, re-exported by `plugin-sdk` | Used in |
|---|---|---|
| `PluginManifest` | `pluginManifestSchema` | `PluginDetail`, `PluginInspection`, `PluginDraft`, `PluginManifestUpdate` |
| `DeclarativeProvider` | `declarativeProviderSchema` | `DraftTestRequest` (and `PluginManifest.contributes.providers`) |
| `McpServerDecl` | `mcpServerDeclSchema` | `PluginManifest.contributes.mcpServers` |
| `CredentialField` | `credentialFieldSchema` | `ProviderSummary.credentialFields` |
| `ModelInfo` | `modelInfoSchema` | `DraftTestResult.models`, `PluginManifest.contributes.models` |
| `SettingsSchema` | `settingsSchemaSchema` | `PluginSettingsView.schema`, `PluginManifest.settings` |
| `ReasoningEffort`, `ToolPolicy` | `reasoningEffortSchema`, `toolPolicySchema` | everywhere |
| `HarnessErrorInit`, `HarnessErrorCode`, `HarnessErrorAction` | section 2 | `ProviderDefinition.mapError()` |

Note: `ai` 7 also exports a type named `ModelInfo`; always import `ModelInfo` from `@harness-forge/shared` or
`@harness-forge/plugin-sdk`, never from `ai`.

### 3.3 Route table

```ts
export type HttpMethod = 'GET' | 'POST' | 'PUT' | 'PATCH' | 'DELETE'
export type ApiResponseSpec = z.ZodType | 'empty' | 'sse' | 'ui-message-stream' | 'binary'

export type ApiModule =
  | 'health' | 'auth' | 'settings' | 'events' | 'providers' | 'credentials' | 'models' | 'icons' | 'chats'
  | 'chat' | 'files' | 'tools' | 'mcp' | 'commands' | 'plugins' | 'pluginInstall' | 'pluginDrafts' | 'pluginFiles'
  | 'data' | 'audio' | 'projects' | 'keys' | 'changes' | 'shellRules' | 'shares'

export interface ApiRouteDef {
  module: ApiModule         // = the key prefix; server route module file = kebab-case of it (plugin-install.ts)
  method: HttpMethod
  path: `/${string}`        // relative to /api, Hono syntax ('/chats/:id'); a trailing '*' is the rest path,
                            // bound to params.path ('/plugins/:id/files/*')
  public?: true             // no session required (default: session required)
  fresh?: true              // ALWAYS requires fresh auth when a password is set; conditional cases
                            // (mcp.create / mcp.update with stdio, pluginInstall.install of a plugin that
                            // requires trust, pluginDrafts.create / pluginDrafts.updateManifest with a stdio MCP
                            // server, plugins.reload of a code plugin, pluginFiles.write / pluginFiles.remove of a
                            // plugin that runs code) are enforced by the server only
  params?: z.ZodType        // path params
  query?: z.ZodType
  body?: z.ZodType          // JSON body
  form?: z.ZodType          // multipart/form-data fields other than the file part named `file`;
                            // a route with `form` accepts multipart (and JSON too when `body` is also set)
  response: ApiResponseSpec // zod schema = JSON body; 'empty' = 204; 'sse' = text/event-stream (ServerEvent);
                            // 'ui-message-stream' = AI SDK UI message stream; 'binary' = raw bytes
  status?: 200 | 201 | 204  // success status; default 200, 204 for 'empty'
}

export const apiRoutes = {
  'health.get': { module: 'health', method: 'GET', path: '/health', public: true, response: healthSchema },
  // ... one entry per endpoint, keyed '<module>.<action>' (section 8 lists every key)
} as const satisfies Record<string, ApiRouteDef>

export type ApiRouteKey = keyof typeof apiRoutes
```

The route table has no flag for secret path params: share tokens (`/share/:token...`) are masked by the server's
access log and error log (`/api/share/[redacted]/...`) and by `redactText`, not by the route table.

Module names (camelCase of the server route module file): `health`, `auth`, `settings`, `events`, `providers`,
`credentials`, `models`, `icons`, `chats`, `chat`, `files`, `tools`, `mcp`, `commands`, `plugins`,
`pluginInstall`, `pluginDrafts`, `pluginFiles`, `data`, `audio` (Phase 6, ADR-029), `projects` (Phase 7, ADR-031),
`keys` (Phase 7, ADR-034), `changes` (Phase 8, ADR-036, ADR-037), `shellRules` (Phase 8, ADR-038; file
`shell-rules.ts`), `shares` (`shares.ts` also serves the public `/share/:token` routes). Action verbs: `list`
(collection GET), `get` (item GET), `create`, `update`, `remove`, plus specific verbs (`test`, `refresh`, `stop`,
`switchBranch`, `deleteMessage`, `deleteAll`, `transcribe`, `speech`, `browse`, `rotate`, `cleanupPreview`, `cleanup`,
`diff`, `git`, `revert`, `undo`, `rewindPreview`, `rewind`, ...).

### 3.4 Client

```ts
export interface ApiClientOptions {
  baseUrl?: string          // default '/api'
  fetch?: typeof fetch      // default globalThis.fetch; the web wraps it (401 unauthorized -> /login)
}
export function createApiClient(options?: ApiClientOptions): ApiClient

// client.<module>.<action>(input?) for every route key '<module>.<action>'
type ApiCallInput<R extends ApiRouteDef> = {
  params?: z.input<R['params']>   // required when the route has params
  query?: z.input<R['query']>
  body?: z.input<R['body']>       // JSON body
  form?: FormData                 // multipart body (routes with `form`)
  signal?: AbortSignal
  headers?: Record<string, string>
}
// Result: zod schema -> Promise<z.output<schema>> (typed, not re-validated at runtime)
//         'empty' -> Promise<void>;  'sse' | 'ui-message-stream' | 'binary' -> Promise<Response> (raw)
```

Examples: `client.chats.list({ query: { q: 'foo' } })`, `client.chats.get({ params: { id } })`,
`client.credentials.set({ params: { id: 'anthropic' }, body: { values: { apiKey } } })`,
`client.files.upload({ form })`, `client.pluginFiles.read({ params: { id, path: 'src/index.ts' } })`,
`client.chats.switchBranch({ params: { id }, body: { messageId } })`, `client.data.import({ form })`,
`client.data.export({ query: { files: false } })` (a raw `Response`), `client.shares.view({ params: { token } })`,
`client.chats.deleteMessage({ params: { id, messageId } })`, `client.audio.transcribe({ form })`,
`client.audio.speech({ body: { text } })` (a raw `Response` with the audio bytes),
`client.projects.browse({ query: { path } })`, `client.chats.list({ query: { projectId: 'none' } })`,
`client.keys.rotate({ body: { confirm: 'ROTATE' } })`, `client.data.cleanup()`,
`client.changes.diff({ params: { id }, query: { source: 'git', path } })`,
`client.changes.rewind({ params: { id }, body: { messageId, conflicts: 'skip' } })`,
`client.shellRules.create({ body: { projectId, prefix: 'pnpm test' } })`.

Behavior: sends `credentials: 'same-origin'`, `Accept: application/json`, `Content-Type: application/json` for JSON
bodies; non-2xx -> throws `HarnessError` (from the envelope, `requestId` from `X-Request-Id`); a network failure or a
non-envelope body -> `HarnessError` with code `internal_error`.

## 4. Schemas

Notation: TypeScript shapes of the zod schemas (`?` = optional key, `| null` = nullable, always present). Unless
noted, strings are trimmed and non-empty in request schemas.

### 4.1 Primitives and enums

| Schema / type | Definition |
|---|---|
| `timestampSchema` / `Timestamp` | integer >= 0, epoch ms |
| `chatIdSchema` / `ChatId` | `^[0-9a-f]{8}-[0-9a-f]{4}-7[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$` (uuidv7) |
| `messageIdSchema` / `MessageId` | `^msg_[0-9A-Za-z]{16}$` |
| `fileIdSchema` / `FileId` | `^file_[0-9A-Za-z]{16}$` |

| Entry | Content |
|---|---|
| `manifest.json` | `BackupManifest`, written last |

stored blob is missing or no longer matches its sha256 is left out (an import counts it in `filesMissing`); a chat
deleted while the zip is written is left out. An import also accepts the same layout inside a single top-level folder.

The sanitizer is an allowlist: it copies only the fields listed above, so an unknown part type or metadata field is
dropped rather than published. Dropped when the snapshot is taken: system messages, chat and global instructions,
`metadata.error` (a failed reply keeps only `status: 'failed'`), usage and cost, `command.expansion` and
`command.input`, provider metadata, approvals, `data-*`, `step-start`, `reasoning-file`, `custom` and unknown parts,
source URLs that are not `http(s)`, and file URLs that are neither `/api/files/<id>` nor a raster image data URL
(never SVG). Reasoning text and tool details are always stored, so an option change applies to the page at once. A
tool input or output is kept as a JSON copy when its JSON text fits in 16384 chars (`LIMITS.shareToolValueChars`; a
string: its length); a longer value becomes a string: the start of its JSON text (or of the string) +
`\n[truncated]`, 16384 chars in total. An error text is cut at 4096 chars. A tool call that never finished shows
`stopped`; an approval that was never answered shows `stopped` on the last message and `denied` when a later message
exists.

### 4.18 Images

ADR-028. Three ways to get an image: an **image turn** with a dedicated image model (`kind: 'image'`, the "Image
models" group of the chat model picker), a **chat model with image output** (`capabilities.imageOutput`, e.g. Gemini
`*-image`), and the builtin **`generate_image` tool** (`core-tools`, policy `ask`, model from the `imageModelRef`
setting). Every generated image is stored as a file (`GET /files/:id`) before it is streamed or saved: no `data:` URL
ever reaches the `messages` table.

```ts
type ImageAspectRatio = '1:1' | '3:2' | '2:3' | '4:3' | '3:4' | '16:9' | '9:16'   // imageAspectRatioSchema
```

Rules (the stream is described in sections 5.10 and 6.8):

- **Image turn**: `POST /chat` with a model of `kind: 'image'`. The prompt is the text of the answered user message
  after slash-command expansion (its text parts joined by line breaks, trimmed); `400` on `['message', 'parts']` when it
  is empty or longer than 32,000 characters (not checked when a reply command answers without the model). Input images:
  when the model has `vision`, the raster images (`GENERATED_IMAGE_MIME_TYPES`) attached to the message (the first 4),
  or, when none are attached and `editPrevious !== false`, the generated images of the parent reply that are still
  stored (the last 4). Attachments the model does not take (other files, images beyond the first 4, every image for a
  model without `vision`) get the `attachments-unsupported` notice when the message is new. An image turn sends no
  history.
- **`imageOptions`** is accepted only for an image model or a chat model with `capabilities.imageOutput`; `n` and
  `editPrevious` only for image models; otherwise `400 validation_error` on `['imageOptions']` (texts in section 5.10).
- **`generate_image`**: the model never sees the output JSON, only the text "Generated 2 images with <model>; they
  are shown to the user below this call." ("Generated 1 image with <model>; it is shown to the user below this
  call."), where `<model>` is `modelName`, else (outputs stored before Phase 7) `modelRef`; the text is built from the
  stored output alone, whenever the history is converted; the output above (file references, well under the 64 KB tool output cap) is stored in the tool part. The chat
  pipeline appends one `file` part per image right after the final `tool-output-available` chunk, only for `core-tools`'
  `generate_image` (also on an approval continuation), only when the output parses with
  `generateImageToolOutputSchema`, and only for images whose URL is `/api/files/<fileId>` of a stored raster image; the
  tool's `costUsd` is added to the cost of the message. The tool is always registered: without an `imageModelRef` it
  fails with "Choose an image model in Settings → Media.", with a `provider_not_configured` error (action
  `configure-provider`) when the provider of the image model is unknown, disabled or lacks credentials (Phase 7: also
  for an unknown provider, which v1.2 reported as `not_found`: 'The provider "<id>" is not available. Pick another
  model or install the provider.'; `ctx.images.generate` throws the same error), and when
  every image was refused (see below) with
  `provider_error` "The image model returned no image that could be stored: only PNG, JPEG, WebP and GIF images of at
  most 20 MB are kept."
- A generated file that is not one of `GENERATED_IMAGE_MIME_TYPES`, exceeds `LIMITS.generatedImageBytes` (20 MB, the
  upload limit, so a backup restores every generated image) or whose bytes do not match its type is dropped and replaced
  in place by a `data-notice` (`generated-file-dropped`, "A file the model generated was not kept: only PNG, JPEG, WebP
  and GIF images up to 20 MB are stored."; for several: "3 files the model generated were not kept: …"). Stored images
  are deduplicated by content: the same bytes reuse the earlier `files` row and its name.
- History (for chat models): every generated file of an assistant message is sent as the text
  `[Generated image: <name>]` (`[Generated file: <name>]` for other types) in its place, so no assistant message reaches
  a provider empty (most providers ignore images in assistant messages); for models with `vision` the images of the
  latest assistant message that has any (the last 4) are also carried into the next user message, before its own
  content, after the text "(Images generated earlier in this chat:)". `reasoning-file` parts are never sent back to
  models.
- Usage: one usage row per generation (purpose `image`, linked to the chat), written as soon as the provider answered
  (also when the run was stopped meanwhile) and counted in `ChatDetail.totals`. The estimated `costUsd` = (input
  tokens × input price + output tokens × output price) / 1,000,000 with the catalog's per-1M-token prices, rounded to
  1e-10; it is absent (null in the row) when the model has no catalog price, when the provider reports no token counts
  (xAI), or when a token kind that was used has no price. Share links and backups treat generated images as ordinary
  `file` parts.

### 4.20 Projects

ADR-031. A project is a named folder on the server host; a chat optionally belongs to one (`ChatSummary.projectId`).
Project folders lie inside the **allowed roots** (`HF_WORKSPACE_ROOTS`, comma list of absolute folders, default

- **Project file**: on every run of a chat model in a project chat, `AGENTS.md`, else `CLAUDE.md`, is read from the
  folder root (never from subfolders) through the workspace path guard: a file that is missing, not a regular file, a
  link out of the folder or binary (a NUL byte in its first 8 KiB) is skipped and the next name is tried. A line made
  only of `@relative/path.md` (a relative path ending in `.md`, surrounding spaces allowed) is replaced by that file
  (one level, inside the folder, at most 64 such lines per file; a refused, missing or binary target leaves the line as
  written). At most 32 KiB in total (`LIMITS.projectFileBytes`, cut at a character boundary), then the marker
  "[The project file was cut at 32 KiB.]" after a blank line. It joins the instructions as "Instructions from
  AGENTS.md in the project folder:" (or `CLAUDE.md`), a blank line and the text.
- **Instructions of a project chat**, in this order (before the `chat.params` hook): global instructions; the workspace
  block (project name, folder, OS and rules for the offered workspace tools); the project file; the project's
  `instructions`; the chat instructions.
- **Steps**: a run in a chat with a project uses the `projectMaxSteps` setting (default 100), also when its folder
  could not be opened; every other run uses `maxSteps` (default 20); both accept 1..200.
- **Opening the folder** (every chat-model run of a project chat; not for image turns or the reply of a slash command
  that answers without the model): the project must still exist and its stored path must still be its own realpath, a
  directory, inside a current root and away from the data directory. Otherwise the run continues without workspace
  tools and its reply starts with the warning notice `workspace-unavailable` ("The project folder <path> is not
  available: <issue>", or "The project of this chat no longer exists."), on every run until the folder is back.

  - `edit_file`: "Edited x: 1 replacement (+a -r lines).", or "Edited x: N replacements." without a diff.
  - `shell`: "Exit code: N", "Stopped after <s> s (timeout)" or "Terminated by signal SIGKILL"; then, when the working
    folder changed, "The working folder is now <endCwd> (the next call starts there)." or the `cwdNote` (Phase 8); then
    a line `stdout:` and the output (trailing newlines trimmed) or "(empty)"; then `stderr:` and its text, only when
    stderr is not empty.
- **Errors the model sees** (the call fails, the run goes on): a refused `cwd` of `shell` is `validation_error` on
  `['cwd']`; `edit_file` explains a missing `old_string` ("… Read the file again and copy the text exactly, including
  whitespace and indentation.") and an ambiguous one ("old_string occurs N times in x. Add more surrounding lines … or
  set replace_all to true …"); a search pattern that runs longer than 20 s stops with "The search timed out — use a
  simpler pattern or a narrower path." (regex and glob matching run in a Worker).
- **Size**: every output is trimmed to about 60 KiB of serialized JSON (`WORKSPACE_LIMITS.outputMaxBytes`), under the
  64 KB host cap of every tool output.
- **Secret-looking paths** (`.env`, `.env.*` except `.env.example` / `.env.sample` / `.env.template`, `*.pem`, `*.key`,
  `id_rsa*`, `id_ed25519*`, `.npmrc`, `.pypirc`, `.netrc`, `*.p12`, `*.pfx`, `credentials*.json`, `secrets.*`; the file
  name, case-insensitive): reading one asks (`ask` and `edits` modes); searches never read one, even with
  `include_ignored` (a single secret-looking file named in `path` is refused). **Hidden paths** (any segment starting
  with `.`, e.g. `.git` hooks, `.github` workflows, `.vscode`): writing one is policy `always`, so it asks in every
  mode; a user override `allow` still applies. The policies check the path as written and the path it resolves to, so
  a link named `notes.txt` that points at `.env` asks as well.
- **`search_files`** searches a folder (walked like `find_files`) or a single file named in `path`; files over 1 MiB
  and files whose first 8 KiB do not look like text are skipped.
- **Shell**: `bash -c` (else `sh -c`) with the server's privileges in the project folder (or `cwd`), no stdin, a minimal
  environment (an allowlist: no `HF_*`, no provider keys, no `NODE_ENV`), its own process group (killed on Stop,
  timeout or server exit; background processes are stopped once the shell exits, also when they closed their pipes).
  Each call is a new process; since Phase 8 (ADR-038) `cd` persists inside the project folder: the folder a command
  ends in (reported through an EXIT trap on file descriptor 3) is where the chat's next call starts (`endCwd` of the
  last `shell` output on the shown path, so it follows versions and survives restarts; checked again when the next call
  starts: a folder that is gone means the project folder and a `cwdNote`); environment variables do not persist. A
  command whose every segment matches a shell rule runs without asking in the `ask` and `edits` modes (section 4.24;
  `allowedBy`). A valid session can approve its own shell calls (accepted risk, ADR-033); `HF_WORKSPACE_SHELL=0`
  removes the tool.

### 4.22 Master key

ADR-034. The master key encrypts every secret and signs sessions, share tokens and approval requests. It comes from
`HF_MASTER_KEY`, else from `<dataDir>/secret.key`; only a key file can be rotated online (`POST /keys/rotate`), a key
from `HF_MASTER_KEY` is rotated offline with the `rotate-key` CLI (`pnpm key:rotate`, new key from
`HF_NEW_MASTER_KEY`).

```ts
type KeySource = 'env' | 'file'         // keySourceSchema
type KeyCheck = 'ok' | 'mismatch' | 'unknown'   // keyCheckSchema: the key in use against the stored key check
                                        // ('unknown': no check stored yet and no stored secret readable with the key
                                        // in use, e.g. a v1.2 database whose secrets could not be read)

type KeyStatus = {                      // keyStatusSchema (GET /keys); never the key
  source: KeySource
  keyVersion: number                    // >= 1; +1 per rotation
  rotatedAt: Timestamp | null           // null = never rotated
  keyCheck: KeyCheck
  secrets: number                       // stored secrets (rows)
  unreadableSecrets: number             // secrets the current key cannot decrypt (another key version, or failing
                                        // decryption; a rotation leaves them unchanged)
  shares: number                        // share links (their URLs change with a rotation)
  pendingApprovals: number              // MESSAGES with at least one open tool approval (a rotation denies them)
  canRotate: boolean                    // source 'file' and keyCheck 'ok'
}

type KeyRotateBody = { confirm: 'ROTATE' }   // keyRotateBodySchema (POST /keys/rotate, fresh auth); strict

type KeyRotationResult = {              // keyRotationResultSchema
  keyVersion: number                    // the new version
  rotatedAt: Timestamp
  secrets: number                       // secrets re-encrypted with the new key
  skippedSecrets: number                // secrets the old key could not read, left unchanged
  shares: number                        // share links whose URL changed (owners copy the new links)
  approvalsExpired: number              // TOOL PARTS whose open approval was denied ("Expired after a key rotation.");
                                        // one message may hold several, so it can exceed KeyStatus.pendingApprovals
  chats: number                         // chats whose pending-approval flag was cleared
  runsStopped: number                   // runs stopped before the rotation
}
```

`GET /keys` only reads: the key state `_keys` (an internal setting) is written by the first v1.3 boot and by a
rotation. When it is missing, the state the boot would record is computed in memory (the key in use, when the secrets
table is empty or a secret of the current key version decrypts; else `keyCheck: 'unknown'`).

### 4.23 Changes and rewind

ADR-036, ADR-037. Before every agent `write_file` / `edit_file` and before every revert, rewind or undo, the server
stores the file's previous state (content-addressed under `<dataDir>/checkpoints/`, never served, never in a backup) and
journals the change (`workspace_changes`: chat, project, message watermark, tool call, before / after SHA-256). Shell
commands and calls of other tools with workspace access `write` / `execute` are journaled as well (`shell` /
`untracked` rows) but never restored. Every path below is project-relative POSIX; the chat's **current** project
counts (rows recorded while the chat belonged to another project are ignored).

```ts
// "This chat": net changes from the journal (works without git)
type ChatChangeStatus = 'added' | 'modified' | 'deleted' | 'unchanged'   // chatChangeStatusSchema: the base (before the
                                        // chat first changed the file) against the disk now
type ChatChangeFile = {                 // chatChangeFileSchema
  path: string
  status: ChatChangeStatus
  edits: number                         // journaled changes of the file in the chat (edits, reverts, rewinds, undos)
  changedOutside: boolean               // the disk differs from the state after the chat's last recorded change
                                        // (another chat, a shell command, an editor)
  revertible: boolean                   // the base state is stored (not too-large or evicted)
  added: number | null                  // lines added / removed, base against disk; null beyond the first 200 files
  removed: number | null                // (LIMITS.changesLineCountFiles), for binary files and over 256 KiB
  lastEditAt: Timestamp                 // the chat's last recorded change of the file
}
type ChatChanges = {                    // chatChangesSchema (GET /chats/:id/changes)
  available: boolean                    // false: no project, or its folder cannot be opened (files empty)
  reason: 'no-project' | 'folder-unavailable' | null   // changesUnavailableReasonSchema; null when available
  projectId: ProjectId | null           // the chat's current project
  files: ChatChangeFile[]               // most recently changed first, <= 500 (LIMITS.changesFilesMax)
  truncated: boolean
  untracked: { shellCommands: number; toolCalls: number }   // journaled changes a rewind cannot restore
}

// Diff of one file (both views)
type ChangeDiffQuery = { source: ChangeSource; path: string }   // changeDiffQuerySchema; path: 1..4096 chars without
                                        // control characters, resolved through the workspace path guard
type FileDiffStatus = 'added' | 'modified' | 'deleted' | 'unchanged' | 'renamed' | 'untracked'   // fileDiffStatusSchema
type FileDiff = {                       // fileDiffSchema (GET /chats/:id/changes/diff)
  source: ChangeSource
  path: string
  origPath: string | null               // the path at HEAD of a renamed file (git view)
  status: FileDiffStatus
  binary: boolean                       // a side has a NUL byte in its first 8 KiB or is not valid text: no diff
  tooLarge: boolean                     // a side is over 1 MiB (LIMITS.changeDiffSideMaxBytes): no diff
  diff: WorkspaceDiff | null            // base against disk (section 4.21: cut to 24 KiB, `truncated`; no hunks when
                                        // unchanged); null when binary, too large or the base is not available
  currentSha: Sha256Hex | null          // the file on disk now (send it back as a revert's expectedSha); null = missing
  baseAvailable: boolean                // chat: the base is stored; git: the file exists at HEAD or is new
}

// "Git": the project folder against HEAD
type GitFileStatus = 'modified' | 'added' | 'deleted' | 'renamed' | 'untracked' | 'conflicted' | 'typechange'
                                        // gitFileStatusSchema (from `git status --porcelain=v2`)
type GitStatusFile = {                  // gitStatusFileSchema
  path: string                          // project-relative (the repository prefix of the project folder removed)
  origPath: string | null               // before a rename
  status: GitFileStatus
  staged: boolean; unstaged: boolean    // changes in the index / in the work tree (untracked files have neither)
}
type GitUnavailableReason = 'no-project' | 'folder-unavailable' | 'git-missing' | 'not-a-repo' | 'refused' | 'timeout'
  | 'failed'                            // gitUnavailableReasonSchema
type GitStatus = {                      // gitStatusSchema (GET /chats/:id/git)
  available: boolean
  reason: GitUnavailableReason | null   // null when available
  branch: string | null                 // null for a detached HEAD or when not available
  head: string | null                   // the HEAD commit id; null for an unborn HEAD (no commit yet)
  prefix: string                        // the project folder relative to the repository root ('' at the root)
  files: GitStatusFile[]                // sorted by path, <= 2000 (LIMITS.gitStatusFilesMax)
  truncated: boolean
}

// Revert, undo, rewind: every one is a batch of journaled writes that can itself be undone
type ChangeRevertBody = {               // changeRevertBodySchema (POST /chats/:id/changes/revert); strict
  source: ChangeSource                  // 'chat': back to the base before the chat; 'git': back to HEAD
  path: string                          // same rules as ChangeDiffQuery.path
  expectedSha?: Sha256Hex | null        // the disk state the client showed (FileDiff.currentSha; null = missing);
}                                       // another one -> 409 stale; omitted = no check
type ChangeUndoBody = {                 // changeUndoBodySchema (POST /chats/:id/changes/undo); strict
  batchId: ChangeBatchId                // a revert, rewind or undo batch of this chat
  conflicts: ConflictHandling           // a file changed since the batch wrote it: skip it, or force the restore
}
type RewindQuery = { messageId: MessageId }   // rewindQuerySchema (GET /chats/:id/rewind)
type RewindBody = {                     // rewindBodySchema (POST /chats/:id/rewind); strict
  messageId: MessageId                  // a user message of the chat
  conflicts: ConflictHandling           // a file changed since the chat's last recorded change: skip it, or force
}
type RewindAction = 'restore' | 'delete' | 'unchanged' | 'unavailable'   // rewindActionSchema ('unavailable': the
                                        // earlier state is not stored, too-large or evicted)
type RewindFile = {                     // rewindFileSchema
  path: string
  action: RewindAction
  conflict: boolean                     // the disk differs from the state after the chat's last recorded change
  edits: number                         // journaled changes of the file in the range
}
type RewindShellCommand = { command: string; at: Timestamp; messageId: MessageId | null }   // rewindShellCommandSchema;
                                        // command cut at 1000 chars (LIMITS.journalCommandMaxChars)
type RewindToolCall = { tool: ToolName; at: Timestamp; messageId: MessageId | null }        // rewindToolCallSchema
type RewindPreview = {                  // rewindPreviewSchema (GET /chats/:id/rewind)
  messageId: MessageId
  files: RewindFile[]                   // most recently changed first, <= 500
  untracked: {                          // changes in the range a rewind cannot undo
    shellCount: number                  // every shell command in the range
    shell: RewindShellCommand[]         // the latest first, <= 50 (LIMITS.rewindUntrackedListMax)
    tools: RewindToolCall[]             // calls of other tools with workspace access write / execute, <= 50
  }
  truncated: boolean
}
type RestoreSkip = {                    // restoreSkipSchema: a file left as it was
  path: string
  reason: 'conflict' | 'unavailable' | 'refused' | 'failed'   // restoreSkipReasonSchema: changed since the last
                                        // recorded change (skip); earlier state not stored; refused by the path guard
                                        // (.git, a link out of the folder, not a regular file); a write error
  message: string                       // safe to show
}
type RestoreResult = {                  // restoreResultSchema (revert, undo, rewind)
  batchId: ChangeBatchId | null         // the batch that recorded the writes (undo it); null when nothing was written
  restored: string[]                    // written back to an earlier content
  deleted: string[]                     // removed (they did not exist at the target state)
  unchanged: string[]                   // already at the target state
  skipped: RestoreSkip[]
}

type WorkspaceChangedData = {           // workspaceChangedDataSchema (event workspace.changed)
  projectId: ProjectId
  chatId: ChatId | null                 // the chat that wrote the files; null when unknown
  batchId: ChangeBatchId | null         // the rewind, revert or undo batch; null for agent tool edits
  source: WorkspaceChangedSource        // 'tool' | 'rewind' | 'revert' | 'undo'
  paths: string[]                       // <= 200 (LIMITS.workspaceEventPathsMax): the first ones when more changed
}
```

- **Base and conflict**: per path, the base is the earliest before-state the chat recorded and the expected state the
  latest after-state; the file conflicts (`changedOutside`, `conflict`) when the disk (SHA-256) differs from the
  expected state.
- **Rewind** is time-based: "the files as they were when message M was sent". It covers every file row of the chat
  recorded after M was sent, on every version of the conversation; edits of other chats are never undone (they show up
  as conflicts). Folders the agent created stay. Running it again resumes a partial rewind (restored files are
  `unchanged`). The conversation is not moved: "Restore files and edit" is a rewind followed by the edit flow
  (ADR-023).
- **Limits**: a before-state over 8 MiB is not stored (`too-large`; the edit still runs); per project 512 MiB and 30
  days (the oldest before-states are evicted; their rows stay as `evicted`).

### 4.24 Shell rules

ADR-038. A shell rule is a command prefix, for one project or for every project (the global list). A `shell` command
runs without asking in the `ask` and `edits` modes when **every** segment (split on `&&`, `||`, `;`, `|` and unquoted
newlines) starts with the words of a rule; the output names the rules (`ShellToolOutput.allowedBy`). Rules are not
settings: they are not in backups (a backup never grants shell rights); deleting a project deletes its rules.

```ts
type ShellRule = {                      // shellRuleSchema
  id: ShellRuleId                       // srl_ + 16 chars, generated by the server
  projectId: ProjectId | null           // null = a global rule (every project)
  prefix: string                        // the canonical prefix: words unquoted, one space between them; <= 200 chars
  createdAt: Timestamp
}
type ShellRuleList = ListResponse<ShellRule>   // shellRuleListSchema (GET /shell-rules)

type ShellRuleCreate = {                // shellRuleCreateSchema (POST /shell-rules); strict, shape only
  projectId: ProjectId | null           // null = a global rule
  prefix: string                        // trimmed, 1..200 chars (LIMITS.shellRulePrefixMaxChars); the server checks it
}                                       // with parseShellRule and stores the canonical form
```

- **Matching** (`matchShellRules(command, rules)` of `@harness-forge/shared`, the same code on the web and the server):
  a rule's words must equal the first words of a segment (`pnpm test` matches `pnpm test --run x`, not `pnpm testx` or
  `pnpm -C x test`); words are compared after unquoting; the command word is literal (`pnpm` is not `./pnpm`). It
  fails closed: a command that cannot be split with certainty always asks.
- **Always asks** (no rule can allow it): `$` (variables, `$(…)`, `$((…))`), backticks, `( ) { }`, `&`, `|&`,
  redirections other than `N>&M`, `>/dev/null`, `N>/dev/null`, `&>/dev/null`; `<`, `<<`, `<<<`, `<(`, `>(`; unquoted
  `*`, `?`, `[`; a word starting with `~` or `#`; shell keywords, `!`, `[[`, `((`; an environment assignment before the
  command (`FOO=1 cmd`); more than 32 segments (`LIMITS.shellCommandSegmentsMax`). `cd <folder>` needs no rule when the
  folder lies inside the project folder; `cd`, `cd -`, `pushd` and `popd` ask.
- **Refused rules** (`400` on `POST /shell-rules`, `parseShellRule` gives the reason and the message): a prefix the
  parser cannot read or that always asks; a first word that runs its arguments as a command (at least `sh`, `bash`,
  `zsh`, `dash`, `ksh`, `fish`, `eval`, `exec`, `source`, `.`, `command`, `builtin`, `env`, `sudo`, `doas`, `su`,
  `xargs`, `nohup`, `nice`, `timeout`, `time`, `watch`, `stdbuf`, `chroot`, `setsid`, `ssh`, `parallel`); a shell
  builtin that changes the shell or evaluates its arguments; a rule for an interpreter or package runner that names no
  script or package (at least `node`, `python`, `python3`, `ruby`, `perl`, `php`, `deno`, `bun`, `npx`, `pnpx`,
  `bunx`); and `cd`, `pushd`, `popd`. The complete word lists live in `util/shell-command.ts`.
- **Suggestions**: `suggestShellRules(command)` gives one prefix per segment that needs a rule (the command word, plus
  the subcommand of tools such as `git`, `npm`, `pnpm`, `yarn`, `cargo`, `go`, `docker`, plus the script name after
  `run` / `exec`), or none when the command always asks.
- **Accepted risk**: a rule for a script runner (`pnpm test`, `make`) runs whatever code the agent wrote into the
  project; with Accept edits this is about as strong as the auto mode for the shell. Arguments can still have side
  effects (`git diff --output=…`).

## 5. Endpoints

Grouped by server route module (`apps/server/src/http/routes/<module>.ts`), exactly as in DECISIONS.md. Each entry:
route key, auth (**public** / session / **fresh**), input, success response, specific errors.

Implicit errors (not repeated below): `401 unauthorized` on every non-public route without a session;
`403 forbidden` on every non-`GET` route failing the Origin check; `400 validation_error` on every route with
params/query/body (except the public share routes, which answer `404`, section 5.20); `413 payload_too_large` when a
body exceeds its limit; `500 internal_error`.

### 5.1 `health.ts`

**`GET /health`** — `health.get` · public
- Response `200 Health`. Used by Docker `HEALTHCHECK`, gate scripts and Settings → About.

### 5.2 `auth.ts`

**`GET /auth/status`** — `auth.status` · public
- Response `200 AuthStatus`.

**`POST /auth/login`** — `auth.login` · public
- Body `LoginBody`.
- Response `200 AuthStatus` + `Set-Cookie: hf_session=...`. When no password is configured: `200` with
  `enabled: false, authenticated: true`, no cookie.
- Errors: `401 unauthorized` (wrong password, message "Invalid password"); `429 rate_limited` (`retryAfterMs`,
  `Retry-After`) after 5 failed checks in 15 minutes from one client address or 50 from all addresses (a correct
  password resets the address). The limiter counts per client address: the TCP peer, unless the peer is a reverse
  proxy trusted by `HF_TRUST_PROXY` (ADR-026), in which case the client is read from `X-Forwarded-For`; without
  `HF_TRUST_PROXY` every client behind a proxy shares the proxy's address (ARCHITECTURE.md 10.1, 10.6).

**`POST /auth/logout`** — `auth.logout` · public
- Response `204`, clears the cookie (`Max-Age=0`). Idempotent.

**`PUT /auth/password`** — `auth.setPassword` · **fresh**
- Body `PasswordUpdate`. `newPassword: null` removes the password.
- Response `200 AuthStatus`; the session epoch is incremented (all other sessions end) and a new cookie is set
  for the caller (none when the password was removed). Every event stream closes (Phase 7: a revoked session must not
  keep listening; the caller's tab reconnects with its new cookie).
- Errors: `403 forbidden` (`currentPassword` missing or wrong); `429 rate_limited` (the current-password check
  shares the login limiter); `409 conflict` (`reason: 'env-password'` when `HF_PASSWORD` is set;
  `reason: 'insecure-bind'` when removing the password on a non-loopback bind without `HF_INSECURE=1`).

### 5.5 `providers.ts`

**`GET /providers`** — `providers.list`

**`PATCH /providers/:id`** — `providers.update`

### 5.6 `credentials.ts`

**`PUT /providers/:id/credentials`** — `credentials.set`
- Params `{ id: ProviderId }`. Body `CredentialsUpdate` (`{ values: Record<string, string> }`).

- Response `200 ProviderSummary`. **Never echoes secret values** (only `SecretState`). Clears `lastError`, emits

- Errors: `404 not_found`; `400 validation_error` (unknown keys, value over 4096 chars, invalid URL in a `url`

**`DELETE /providers/:id/credentials`** — `credentials.clear`
- Params `{ id: ProviderId }`.
- Response `200 ProviderSummary`. Removes every stored value of the provider (env fallbacks keep working). Emits

- Errors: `404 not_found`.

### 5.7 `models.ts`

**`GET /models`** — `models.list`
- Query `ModelsQuery`.
- Response `200 ListResponse<CatalogModel>`: models of enabled providers (regardless of credential status; the web

- Errors: `404 not_found` (unknown provider; not routed through the model resolvers, so not

- Body `CustomModelInput`. Creates or replaces the custom model (`model_prefs.custom = 1`, `info`).

- Errors: `404 not_found` (unknown provider).

**`DELETE /custom-models?providerId=&modelId=`** — `models.removeCustom`
- Query `CustomModelKey`.
- Response `204`. Emits `catalog.changed`.
- Errors: `404 not_found` (no custom model with that key).

### 5.9 `chats.ts`

**`GET /chats`** — `chats.list`

**`POST /chats`** — `chats.create`
- Body `ChatCreate`. Without `messages` it creates an empty chat; with `messages` it imports them (e.g. the
  `chat` of a JSON export): deep-validated with `validateUIMessages`, `seq` from array order, invalid, repeated or
  already used message ids replaced with new ones (`parentIds` and `activeLeafId` follow), pending approvals resolved
  as denied. Without `parentIds` the import is linear; with `parentIds` there is one per message, every parent must
  be `null` or the id of an earlier message, and the ids must be unique. The tree is validated before anything is
  written; the chat, its messages and its active leaf are inserted in one batch. The active leaf is the most recent
  leaf under `activeLeafId` (default: the last message). Body limit 20 MB (imports), <= 2000 messages.
- `projectId` puts the new chat in a project (ADR-031); an import never takes a project from the uploaded export.
- Response `201 ChatDetail`. Emits `chat.created`.
- Errors: `404 not_found` (unknown `projectId`, "Project <id> not found."; nothing is written); `409 conflict`
  (`reason: 'exists'`, `chatId`: the chat id is already used; checked first); `400 validation_error`
  (`details.issues[].path` names the field: `parentIds` for a count that differs from `messages`,
  `['parentIds', i]` for a parent that is not an earlier message, `['messages', i, 'id']` for a repeated id when
  `parentIds` is sent, `activeLeafId` for an id that is not in `messages`, `['messages', i, ...]` for a message that
  fails `validateUIMessages`). The single-chat import of `POST /data/import` reports the same issues under `chat`
  (`['chat', 'parentIds', 1]`).
- Note: the normal "new chat" flow does not call this: the web generates a uuidv7 and the first `POST /chat`
  creates the chat.

**`GET /chats/:id`** — `chats.get`
- Params `{ id: ChatId }`.
- Response `200 ChatDetail`: `messages` = the active path (first message -> active leaf, `seq` order), `branches` =
  the versions of the path messages that have siblings. During a run the path ends at the message committed when the
  run started (section 6.6).
- Errors: `404 not_found`.

**`PATCH /chats/:id`** — `chats.update`
- Params `{ id: ChatId }`. Body `ChatUpdate`.
- Response `200 ChatSummary`. Emits `chat.updated`. A `title` sets `titleSource: 'user'` (never overwritten by
  auto titles).
- `projectId` moves the chat (ADR-031): a project id puts it in that project, `null` takes it out. The next run uses
  the new project's folder and instructions; the messages are unchanged. Like every `PATCH` of a chat, a move keeps
  `updatedAt` (the chat keeps its place in the list). The project is checked by the update itself (`UPDATE … WHERE
  EXISTS`), so a project deleted meanwhile leaves no dangling id.
- Errors: `404 not_found` (unknown chat; or unknown `projectId`, "Project <id> not found.": the whole patch is dropped,
  its other keys included); `409 conflict` (`reason: 'run-active'`, `chatId`) whenever `projectId` is in the patch
  (also `null`) while a run holds the chat, in any phase: nothing of the patch is applied.

**`DELETE /chats/:id`** — `chats.remove`
- Params `{ id: ChatId }`.
- Stops an active run first, deletes the chat, its messages (every version) and its share links (cascade); usage
  rows are kept with `chat_id = NULL`; uploaded files are kept (content-addressed, shared).
- Response `204`. Emits `chat.deleted`.
- Errors: `404 not_found`.
- Note: "Undo" in the UI delays this call (toast), the server has no soft delete.

**`GET /chats/:id/export?format=md|json`** — `chats.export` · response `'binary'`
- Params `{ id: ChatId }`. Query `ChatExportQuery`.
- Response `200` with `Content-Disposition: attachment; filename="<title-slug>-<yyyy-mm-dd>.<md|json>"`:
  - `format=json`: `application/json; charset=utf-8`, body `ChatExport` (version 2: every message version,
    `parentIds`, `activeLeafId`; never `projectId`, ADR-031).
  - `format=md`: `text/markdown; charset=utf-8`, the active path: `# <title>`, an export line (date, model), then one
    section per message (`## User` / `## Assistant (<modelRef>)`): text parts verbatim, reasoning as a `> ` quote
    block, tool calls as `**Tool** \`<name>\` (<state>)` with input and output in fenced `json` blocks (output
    truncated at 4 KB), files as `[name](url)`.
- Errors: `404 not_found`.

**`POST /chats/:id/branch`** — `chats.switchBranch`
- Params `{ id: ChatId }`. Body `ChatBranchBody` (`messageId`: any message of the chat, ADR-023).
- Shows the path last shown under `messageId` (ADR-030): every message remembers the child last shown under it, so
  from `messageId` down the path follows each remembered child while it is still a child, else the only child; at a
  message with several children and no valid remembered one it ends at the most recent leaf (the highest `seq`) under
  that message. That leaf becomes the active leaf and the shown path is remembered in the same write, so switching away
  and back restores it. `pendingApproval` is recomputed from the new path (approvals on other versions stay pending
  and are live again when their version is shown); `updatedAt` is not changed.
- Response `200 ChatDetail` (the new path and its `branches`). Emits `chat.updated` (`ChatUpdatedData`: other tabs
  that show the chat follow the new `activeLeafId`).
- Errors: `404 not_found` (unknown chat, "Chat <id> not found.", or `messageId` not in the chat, "Message <messageId>
  not found in chat <id>."); `409 conflict` (`reason: 'run-active'`, `chatId`) while a run holds the chat, in any
  phase ("A reply is already being generated for this chat. Stop it or wait until it finishes."), and when the active
  leaf moved between reading and switching it (a compare-and-set: a run committed or another switch won meanwhile; "The
  chat changed while switching versions. Wait until the reply finishes, then try again."). After a missed
  compare-and-set the error is derived again: `404` when the chat or the message is gone by then.

**`DELETE /chats/:id/messages/:messageId`** — `chats.deleteMessage`
- Params `ChatMessageParams` (`messageId`: any message of the chat that has another version, ADR-030).
- Deletes one version and every message after it (the message and its whole subtree). When the active path goes
  through it, the path moves to what was last shown under the previous version (the previous sibling by `seq`, else
  the next one), as `POST /chats/:id/branch` shows it, and that path is remembered; `pendingApproval` is recomputed and
  `updatedAt` is kept. Usage rows (totals keep counting deleted versions), share links (their snapshots) and uploaded
  or generated files are untouched; the search text goes with the deleted messages. Deleting a version that is not on
  the active path leaves the path as it is.
- One atomic write: the leaf moves under a compare-and-set against the leaf read before, and the subtree is deleted
  only while the leaf is where the delete expects it and another version of the message still exists, so a race never
  deletes the shown path or the last version.
- Response `200 ChatDetail` (the path and its `branches` after the delete). Emits `chat.updated` (`ChatUpdatedData`),
  also for a version off the active path (with the unchanged leaf).
- Errors (nothing is deleted):
  - `404 not_found`: unknown chat ("Chat <id> not found.") or `messageId` not in the chat ("Message <messageId> not
    found in chat <id>.").
  - `409 conflict`, `reason: 'only-version'` (no `chatId`): the message has no other version ("This is the only
    version of the message. Delete the chat instead.").
  - `409 conflict`, `reason: 'run-active'`, `chatId`: a run holds the chat, in any phase (checked first: "A reply is
    already being generated for this chat. Stop it or wait until it finishes."), or the active leaf moved meanwhile
    ("The chat changed while deleting the version. Wait until the reply finishes, then try again."). After such a
    missed compare-and-set the error is derived again: `404` when the chat or the message is gone by then,
    `only-version` when the other versions were deleted meanwhile.

### 5.10 `chat.ts`

**`POST /chat`** — `chat.send` · response `'ui-message-stream'`
- Body `ChatRequestBody` (max 2 MB).
- Response `200` AI SDK v7 UI message stream (section 6). Errors that happen before the stream starts are normal
  JSON error responses: `400 provider_not_configured` (action `configure-provider`); `404 not_found` (`parentId` or
  `messageId` not in the chat, or a continuation that is not the active leaf); `409 conflict` (`reason: 'run-active'`,
  `chatId`; `reason: 'exists'` when the new user message id is already stored; `reason: 'stale'`, `chatId`, when the
  run was stopped (Stop, delete-all, shutdown) before its history was stored; `reason: 'busy'` while a master-key
  rotation runs, checked before anything is written: "The server is rotating its encryption key. Try again in a
  moment.", section 5.23); `400 validation_error` (including
  `validateUIMessages` failures, file parts whose `url` is not `/api/files/<id>`, a user message sent with
  `messageId` (issue path `messageId`), `parentId` on a regenerate or a continuation (`parentId`), a regenerate with
  no user message to answer (`messageId`: an empty chat, or a target whose previous message is not a user message),
  and a continuation that carries no approval decision (`['message', 'parts']`)). Section 6.2 lists what each action
  sends.
- Such an error stores no message: at most the chat row is created (a new chat id, with `chat.created`) or its model,
  mode and effort are updated, so the web can send the same text again under a new message id.
- Projects (ADR-031): `projectId` is honored only by the request that creates the chat: an unknown project is
  `404 not_found` before the chat row exists; for an existing chat it is ignored. In a chat with a project, every
  chat-model run opens the project folder (section 4.20; not image turns, not the reply of a slash command that
  answers without the model): the workspace tools are offered (`shell` and every other `execute` tool only while
  `HF_WORKSPACE_SHELL` is not `0`), `ToolCallContext.workspace` is set for every tool of the run (policy functions
  receive it too; hooks get no project data), the instructions gain the workspace block, the project file and the
  project instructions, and the run uses `projectMaxSteps`. A folder that cannot be opened gives the warning notice
  `workspace-unavailable` (on every such run) and a run without workspace tools, still with `projectMaxSteps`; a chat
  without a project is never offered a tool that declares `workspace`.
- `toolMode: 'edits'` (Accept edits, ADR-032): approvals follow the table of section 6.7.
- Images (ADR-028, section 4.18): the catalog kind of `modelRef` decides. A model of `kind: 'image'` makes the request
  an **image turn** (no history is sent; the prompt and the input images as in section 4.18); the reply streams one
  `file` chunk per image (section 6.8). An image model whose provider has no `createImageModel` (only a custom model
  can be one) is `404 model_not_found` ("The provider "<name>" cannot generate images, so the model "<ref>" cannot be
  used."). More `400 validation_error`s, checked after the model resolved:
  - `imageOptions` with a model that is neither an image model nor a chat model with `capabilities.imageOutput`
    (`['imageOptions']`: "The model "<ref>" does not generate images: image options are only for image models and chat
    models with image output."), or `n` / `editPrevious` with a chat model with image output (`['imageOptions']`: "A
    chat model with image output takes only the aspect ratio: n and editPrevious are for image models.");
  - an approval continuation sent with an image model (`['modelRef']`: "An image model cannot continue a tool call.
    Pick a chat model to answer the pending tool call.");
  - an image turn whose prompt is empty (`['message', 'parts']`: "Describe the image to generate: an image model needs
    a text prompt.") or longer than 32,000 characters (`['message', 'parts']`: "Image prompts are limited to 32000
    characters.").
- Image turns are sent, edited, regenerated, stopped, resumed and branched like other replies. An image model that
  returns no image ends the reply with `provider_error` ("<Provider> returned no image."). The title of a new
  image-turn chat comes from `titleModelRef`, else the provider's `smallModelId` (a title model that fails gives the
  first 60 characters of the message, as for chat runs); without either the default title stays: the image model is
  never asked for a title.
- Generated files never travel as `data:` URLs: files a chat model generates (image output, also inside reasoning) and
  the images of the `generate_image` tool are stored first and streamed as `file` chunks with `/api/files/<id>` URLs;
  the stored message equals the streamed one. A generated file that cannot be stored is replaced in place by a
  `data-notice` (`generated-file-dropped`).

**`GET /chat/:id/stream`** — `chat.resume` · response `'ui-message-stream'`
- Params `{ id: ChatId }`. This is the default reconnect URL of `DefaultChatTransport` (`{api}/{chatId}/stream`).
- Response `200` stream (the active run replayed from its first chunk, then live chunks), or
  `204 No Content` when there is nothing to resume (idle or unknown chat).

**`POST /chat/:id/stop`** — `chat.stop`
- Params `{ id: ChatId }`. No body.
- Response `200 ChatStopResult` (`stopped: false` when no run was active). The run is aborted, the partial message
  is persisted with `metadata.aborted = true`, `run.finished` is emitted with `outcome: 'aborted'`.

### 5.16 `plugin-install.ts`

**`POST /plugins/inspect`** — `pluginInstall.inspect` · JSON or multipart
- Body `PluginInspectBody` (JSON), or `multipart/form-data` with the zip in part `file` (<= 20 MB).
- Fetches/extracts into `plugins/.staging/<uuid>` with all install guards, validates, reports, then deletes the
  staging dir. Nothing is installed.
- Response `200 PluginInspection`.
- Errors: `400 validation_error` (invalid manifest, zip guard violation, integrity mismatch, folder is not a

  server; ADR-017), with or without `trust`. A code plugin installed without `trust` ends `untrusted` (inert) until
  `POST /plugins/:id/trust`.
- Installs via staging + atomic swap (ARCHITECTURE.md 6.5). Same id and same source = update (the previous
  version is restored if the new one fails to load).
- What was reviewed is what gets installed: `sha256` (optional) is the hash shown by `inspect`. The server also
  remembers the hash of npm and folder sources inspected in the last 30 minutes; when the source now yields other

- Response `201 PluginDetail`. Emits `plugin.changed` (+ `catalog.changed`, `provider.changed`).
- Errors: as `inspect`; `400 validation_error` (incompatible `engines.harness`); `403 forbidden` (reserved or

  `reason: 'stale'`, the package changed since it was reviewed).

- Params `{ id: PluginId }`. Body `PluginTrustBody`.
- Pins `trusted_hash` (for `link`: pins the realpath) and reloads if enabled.
- Response `200 PluginDetail`.
- Errors: `404 not_found`; `409 conflict` (`reason: 'stale'`, `sha256` differs from the current hash: the files

**`GET /plugins/:id/export`** — `pluginInstall.export` · response `'binary'`
- Params `{ id: PluginId }`.
- Response `200 application/zip`, `Content-Disposition: attachment; filename="<id>-<version>.zip"`: the plugin

- Errors: `404 not_found`; `403 forbidden` (builtin).

### 5.18 `plugin-files.ts`

Path rules for `*` (`params.path`): relative POSIX path, 1..256 chars, segments of `[A-Za-z0-9._-]`, at most 8
segments; no leading `/`, no `.` or `..` segments, no backslashes, no NUL; resolved with `realpath` inside the
plugin dir. Violations -> `400 validation_error`. Files are text only (valid UTF-8, no NUL) and at most 1 MB.

Additional guards (all `400 validation_error`):

- `.git` and `node_modules` are never listed or opened, even for reading.
- Hidden files and folders (a segment starting with `.`) are listed with `editable: false` and cannot be created,
  changed or deleted, so a stolen session cannot plant `.git/hooks` or editor tasks in a linked folder.
- Symbolic links are neither listed nor followed; a path that differs only in letter case from an existing entry
  (`PLUGIN.JSON`) is refused.

**`POST /plugins/scaffold`** — `pluginFiles.scaffold` · **fresh**
- Body `ScaffoldRequest`. Creates `data/plugins/<id>/` from the template (`plugin.json` + `index.mjs` or
  `index.ts`), `source: 'created'`, trusted (hash pinned), enabled and loaded.
- Response `201 PluginDetail`.
- Errors: `403 forbidden` (reserved id); `409 conflict` (`reason: 'exists'`).

**`GET /plugins/:id/files`** — `pluginFiles.list`
- Params `{ id: PluginId }`.
- Response `200 ListResponse<PluginFileEntry>`: recursive (at most 8 levels), directories first then files, sorted
  by path; skips `node_modules`, `.git`, symbolic links and temporary files of atomic writes (build output lives in
  `data/cache/plugins/<id>/`, outside the plugin dir); at most 2000 entries.
- Errors: `404 not_found`; `403 forbidden` (builtin).

**`GET /plugins/:id/files/*`** — `pluginFiles.read`
- Params `PluginFileParams`.
- Response `200 PluginFileContent`.
- Errors: `404 not_found`; `400 validation_error` (bad path, binary file); `413 payload_too_large` (> 1 MB);
  `403 forbidden` (builtin).

**`PUT /plugins/:id/files/*`** — `pluginFiles.write` · **fresh** for plugins that run code
- Params `PluginFileParams`. Body `PluginFileWrite` (creates missing parent directories).
- Writes are atomic and never trigger the file watcher. `plugin.json` must stay a valid manifest with the same id.
  Declarative plugins reload when `plugin.json` is written; code changes take effect on `POST /plugins/:id/build`.
- Fresh auth (ADR-017): writing a file of a plugin that runs code (a code plugin or a stdio MCP server), or a
  `plugin.json` that would make it run code, requires fresh auth when a password is set.
- Trust (ADR-017): a write to a plugin with source `created` re-pins its trust hash only when the plugin was trusted
  before the write (or needed no trust); a plugin whose files had already changed outside the editor stays
  `untrusted` (a `warn` entry in its log) until it is trusted explicitly. For source `copy` a change of the hashed
  files (`plugin.json`, the entry) makes a code or stdio-MCP plugin `untrusted` until it is trusted again; `link`
  plugins are pinned by path.
- Response `200 PluginFileEntry`.
- Errors: `404 not_found` (plugin); `403 forbidden` (not editable); `409 conflict` (`reason: 'stale'`);
  `400 validation_error`; `413 payload_too_large`.

**`DELETE /plugins/:id/files/*`** — `pluginFiles.remove` · **fresh** for plugins that run code
- Params `PluginFileParams`. Deletes one file (not a folder); directories left empty are removed. Rename in the
  editor = write the new path, then delete the old one. `plugin.json` and the files it references (the `main` entry
  and a file `icon`) cannot be deleted.
- Fresh auth and trust: as for writes (plugins that run code need fresh auth; a trusted `created` plugin is
  re-pinned automatically).
- Response `204`.
- Errors: `404 not_found` (plugin or file); `403 forbidden` (not editable, builtin); `400 validation_error` (bad
  path, a folder, `plugin.json` or a file it references).

**`POST /plugins/:id/build`** — `pluginFiles.build` · **fresh**
- Params `{ id: PluginId }`. Body `PluginBuildBody`.
- Compiles/checks the entry with esbuild (`.ts`: bundled into `data/cache/plugins/<id>/<sha256>.mjs` with the SDK
  aliased to the host shim; `.mjs`/`.js`: syntax and import check), collects diagnostics, and when there are no
  errors re-pins the trust hash of a `created` plugin (the hash of the files that were built) and (if `reload`)
  reloads the plugin; a failed reload is added as an error diagnostic. Build log lines are written to the plugin log
  (`plugin.log` events).
- Response `200 BuildResult` (a failed build is `ok: false` with diagnostics, not an HTTP error).
- Errors: `404 not_found`; `403 forbidden` (not editable, builtin, declarative plugin).

### 5.19 `data.ts`

Bulk data (ADR-024, formats in section 4.16) and the orphaned file cleanup (ADR-035; automatic since Phase 8 when the
`fileSweep` setting is on, ADR-039). Maintenance operations run one at a time: an import, delete-all, file cleanup (its preview included) or key rotation (section 5.23) started while another
one runs gets `409 conflict` (`reason: 'busy'`, "Another data task is running. Try again when it finishes."). No new
event types: the chat events of section 7 report the changes.

**`GET /data`** — `data.summary`
- Response `200 DataSummary` (what a backup contains and what delete-all removes), with the state of the automatic file
  sweep (`fileSweep`, Phase 8) and, optionally, the disk use of the stored workspace before-states (`checkpoints`; never
  part of a backup).

**`GET /data/export?files=true|false&settings=true|false`** — `data.export` · response `'binary'`
- Query `DataExportQuery` (both default `true`).
- Response `200 application/zip`, streamed while it is downloaded, with
  `Content-Disposition: attachment; filename="harness-forge-backup-<yyyy-mm-dd>.zip"` and `Cache-Control: no-store`;
  the layout of section 4.16 (`manifest.json` last). A `HEAD` request runs the pre-check and gets the headers only (no
  zip is built).
- Errors: `413 payload_too_large` from the pre-check (before any byte is sent) when the backup would hold more than
  `LIMITS.backupEntriesMax` (50,000) entries or `files/index.json` items (what an import accepts) or is estimated
  above 3.5 GB (fflate writes no zip64). The message suggests `files=false` only when the backup would fit without
  attachments. If the chats grow past the zip limits while the zip is streamed, the stream fails instead of producing
  a broken archive.

**`POST /data/import`** — `data.import` · multipart
- Body `multipart/form-data`: exactly one upload in part `file` + the `DataImportForm` fields (an unknown or repeated
  field -> `400`); limit 256 MB (`LIMITS.backupImportBytes`). The route reads the multipart body itself, so the upload
  is held once. The first bytes decide the kind: `PK` = a backup zip, `{` (after an optional UTF-8 BOM and
  whitespace) = one chat JSON (`ChatExportAny`, version 1 or 2, at most 64 MB).
- Backups are read lazily with the plugin installer's zip guards (path traversal, symbolic links, duplicate names,
  overlapping entries, at most 50,000 entries, declared and actual sizes, CRC); the declared sizes add up to at most
  8 GB; each chat entry is at most 64 MB and each file blob at most 20 MB before it is inflated. The layout may sit
  inside a single top-level folder; unknown entries become `warnings`.
- What a problem fails:
  - **the whole upload** (an HTTP error, nothing imported): not a zip or a chat JSON; a damaged zip or a zip guard
    violation; a missing, invalid or newer `manifest.json` (`version` or `chatExportVersion`); an invalid
    `files/index.json`; a chat JSON that is invalid (issue paths under `chat`, e.g. `['chat', 'parentIds', 1]`) or
    of a newer version.
  - **one chat of a backup** (`status: 'failed'` + `error`; the other chats go on): a chat entry that is damaged (CRC,
    inflated size), over 64 MB, not a valid chat export, or whose messages or message tree are invalid.
  - **one attachment** (`filesMissing` + a warning; the chat is still imported with the part URL unchanged): a blob
    absent from the upload, over 20 MB, damaged, not matching its sha256 or of a type that is not allowed, unless a
    file with the same id (and content) is already stored here (then it is reused).
- Chats are imported one at a time in entry name order, each atomically: `skip` keeps an existing chat with the same
  id, so running the same import again changes nothing; `copy` imports it under new chat and message ids with
  " (imported)" appended to the title. Title, pinned, archived, dates, model, settings and every message version (the
  tree and the active leaf) are restored; message ids are kept unless another chat uses them; pending approvals are
  resolved as denied. The attachments of a chat are imported before it: re-hashed against `files/index.json`,
  re-checked (type), reused when the same content is stored, and the `/api/files/<id>` URLs of its `file` and
  `reasoning-file` parts rewritten to the stored ids.
- `restoreSettings=true` applies the known keys of `settings.json`, each validated on its own (unknown and invalid keys
  become warnings; with a chat JSON it only adds a warning); secrets and the password are never part of a backup.
- Response `200 DataImportResult`. Emits `chat.created` for every imported or copied chat.
- Errors: `400 validation_error` (the whole-upload failures above); `409 conflict` (`reason: 'busy'`);
  `413 payload_too_large` (an upload over 256 MB, a chat JSON over 64 MB, a backup whose entries declare more than
  8 GB in total).

**`POST /data/delete`** — `data.deleteAll` · **fresh**
- Body `DataDeleteBody` (`confirm` must be the literal `DELETE`).
- Stops every run (runs still preparing included), then deletes every chat with its messages and share links in one
  batch; `usage: true` also deletes every usage row, the rows kept from chats deleted earlier included (else they are
  kept with `chat_id = NULL`); `files: true` also deletes every uploaded file (rows and blobs); finally it stops any
  run that started meanwhile on a deleted chat. Settings, providers, credentials, plugins, MCP servers and projects are
  kept (projects keep no chats).
- Response `200 DataDeleteResult`. Emits `chat.deleted` for every deleted chat.
- Errors: `403 forbidden` (fresh auth missing, `action: 'login'`); `409 conflict` (`reason: 'busy'`).

**`GET /data/cleanup`** — `data.cleanupPreview`
- A dry run of `POST /data/cleanup` (ADR-035): reads every reference, deletes nothing, writes nothing (`lastRunAt`
  stays). It skips the DELETE re-check of a real run (below), so it may count a file that a message committed after
  the scan keeps. `GET /data` stays cheap and does not scan.
- Response `200 DataCleanupPreview` (count meanings in section 4.16), with the automatic sweep state (`fileSweep`) and
  how much of the plugin data the scan read (`pluginData`, Phase 8).
- Errors: `409 conflict` (`reason: 'busy'`).

**`POST /data/cleanup`** — `data.cleanup`
- No body. Run from Settings -> Data, or automatically by the opt-in `fileSweep` setting (Phase 8, ADR-039, below).
- Removes the file rows that nothing references and that are older than 24 hours (`graceMs`), then the leftover blobs
  that no row has (older than 24 hours) and temp files of interrupted uploads older than 1 hour. A blob of a removed
  row is unlinked only when no other row shares it (identical uploads share one blob). References are file ids
  (`file_` + 16 letters or digits) found anywhere in message parts and metadata, share snapshots and their file lists,
  plugin storage (keys and values) and plugin settings, settings, chat settings and projects, and since Phase 8 the
  files of `<dataDir>/plugins/.data` (a loose scan: it may keep an extra file, never removes a referenced one; the
  plugin data scan has a budget, `pluginData: 'partial'` when it stopped early). Workspace before-states
  (`<dataDir>/checkpoints`) are never touched. The DELETE re-checks the message references, so a message committed
  after the scan keeps its file; files returned by an upload, import or image generation within the last 24 hours are
  pinned in memory and kept (`recentFiles`). Deleting a chat or a message version leaves its files in place until the
  next cleanup.
- Response `200 DataCleanupResult`; `ranAt` is stored as the next preview's `lastRunAt`. One info log line with the
  counts (no ids, names or paths). Emits no event.
- Errors: `409 conflict` (`reason: 'busy'`).
- **Automatic sweep** (Phase 8, ADR-039): with `fileSweep` `daily` or `weekly`, a timer of the data service runs the
  same cleanup at least 24 hours after the server started and once `lastRunAt` + the interval has
  passed (a manual cleanup resets the clock); it checks hourly. Another maintenance operation makes it retry in 10
  minutes (nothing stored); a plugin data scan over its budget skips it (`status: 'skipped'`, `reason:
  'plugin-data-limit'`, nothing deleted); a failure is stored and retried after a full interval. The outcome is stored
  as `_files.lastAutoSweep` and reported as `fileSweep.lastAttempt` of `GET /data` and `GET /data/cleanup`; no route,
  no event.

### 5.20 `shares.ts`

Read-only share links (ADR-025, DTOs in section 4.17). The owner routes need a session; creating and changing a link
also need fresh auth (a link turns brief session access into lasting remote access), revoking does not. The two
`/share/:token` routes are **public** and read only the stored snapshot (never live messages; they write nothing, no
view counters); the chat must still exist. The token is never stored: the owner can copy `path` again, revoking
deletes the row, a new master key invalidates every link. The passwordless host guard is unchanged, so exposing links
requires `HF_PASSWORD`. Every response carries `X-Robots-Tag: noindex, nofollow`; tokens are masked in logs. Share
actions emit no server event (the owner UI refetches).

**`GET /shares?chatId=`** — `shares.list`
- Query `SharesQuery`.
- Response `200 ListResponse<ShareSummary>`, newest first.

**`POST /shares`** — `shares.create` · **fresh**
- Body `ShareCreate`. Snapshots the chat's active path through the allowlist sanitizer (section 4.17).
- Response `201 ShareSummary`.
- Errors: `404 not_found` (unknown chat); `400 validation_error` (issue path `expiresAt`: not in the future or more
  than 365 days ahead; `chatId`: the chat already has `LIMITS.sharesPerChatMax` (20) links); `413 payload_too_large`
  (the snapshot exceeds 10 MB, `details.limitBytes`); `403 forbidden` (fresh auth missing, `action: 'login'`).

**`PATCH /shares/:id`** — `shares.update` · **fresh**
- Params `{ id: ShareId }`. Body `ShareUpdate`. `refresh: true` re-snapshots the chat's current active path; changed
  `options` apply to the share page at once; the token and `path` never change.
- Response `200 ShareSummary`.
- Errors: `404 not_found` (unknown share); `400 validation_error` (`expiresAt`); `413 payload_too_large` (refreshed
  snapshot); `403 forbidden` (fresh auth missing, `action: 'login'`).

**`DELETE /shares/:id`** — `shares.remove`
- Params `{ id: ShareId }`. Revokes the link: the row is deleted and the token stops working at once.
- Response `204`.
- Errors: `404 not_found`.

**`GET /share/:token`** — `shares.view` · public
- Params `SharePublicParams`.
- Response `200 ShareView` (the share's options applied at every request: reasoning, tool details and file parts left
  out when disabled; file URLs rewritten to `/api/share/<token>/files/<fileId>`), `Cache-Control: no-store`.
- Errors: `404 not_found`, the same response (message "This share link is unavailable.") for every failure: a
  malformed, unknown, bad-MAC, revoked or expired token, or a deleted chat (never `400`); `429 rate_limited`
  (`retryAfterMs`, `Retry-After`).
- Rate limits (in memory, sliding windows, keyed by the client address of section 1, ADR-026 for proxies): 60 views
  per minute per address; 20 refused tokens per 10 minutes per address, after which the address is refused on both
  public routes until the oldest refusal leaves the window; 6000 requests per minute over both routes and every
  address. A refused request is not counted.

**`GET /share/:token/files/:fileId`** — `shares.file` · public · response `'binary'`
- Params `ShareFileParams`. Serves only the files whose `/api/files/<id>` URLs are in the share's snapshot, and only
  while `options.attachments` is on.
- Response `200` bytes with the headers of `GET /files/:id` (type, `Content-Length`, `nosniff`, sandboxing CSP,
  `inline` only for raster images and PDF) except `Cache-Control: no-store` and no `ETag` (a revoked link stops
  serving at once, caches included). `HEAD` gets the headers only.
- Errors: the same `404 not_found` (also for a file that is not part of the share, attachments turned off, a malformed
  file id or a deleted file); `429 rate_limited`: 600 requests per minute per client address, plus the refused-token
  and global limits of `GET /share/:token`. A failure that is only about the file does not count as a refused token.

### 5.21 `audio.ts`

Voice (ADR-029, DTOs in section 4.19). Both routes need a session and pass the Origin check; they need no fresh auth
(they run no code and create nothing lasting). Nothing is stored: the audio or the text goes to the provider of the
chosen model and the result comes back.

Common rules:

- **Model errors** (resolver errors pass unchanged): `400 validation_error` on `['modelRef']` when no model is given and
  none is set in Settings ("Choose a speech-to-text model in Settings → Media." / "Choose a read-aloud model in
  Settings → Media."), when the model is of another kind ("modelRef: The model "<ref>" is not a speech-to-text model."
  / "… is not a text-to-speech model.") or when its provider cannot serve it ("modelRef: The provider "<name>"
  cannot transcribe speech, so the model "<ref>" cannot be used." / "… cannot read text aloud, …"; only a custom
  model can be one, section 4.5); `400 provider_not_configured` (action `configure-provider`) for an unknown
  provider (Phase 7: as in the chat pipeline, `ctx.images` and `generate_image`; v1.2 answered `404 not_found`), a
  disabled provider or missing credentials; `404 model_not_found` (action `refresh-models`) for a model that is not in
  the catalog;
  `500 plugin_error` when the provider's model factory throws, takes longer than 5 s or returns no model.
- **Provider errors** are mapped as in section 2.3 (`auth_invalid`, `rate_limited`, `model_not_found`,
  `provider_unreachable` (also for the timeout), `provider_error`, with `providerId` and `status` when known) and
  recorded as the provider's call outcome (its status). A speech error whose message (or upstream detail) repeats any
  24 characters in a row of the text (the whole text when it is shorter) is replaced by "<Provider> returned an
  error.", so the text never reaches a log.
- **Canceled requests**: the request signal aborts the provider call when the client disconnects; the (unread) answer
  is `400 validation_error` "The request was canceled.", and neither a provider outcome nor a usage row is recorded.
- **Usage and outcome**: only a `200` answer writes a usage row (purpose `transcription` or `speech`, no chat, 0
  tokens, no cost) and records the provider as working.
- **Logs**: one info line per provider call (`audio transcription` / `audio speech`) with `providerId`, `modelId`,
  `bytes` (the recording, or the returned audio) or `chars` (the speech text length), `type`, `durationSec` (when the
  provider reports it), `ms` and `outcome` (`ok`, `empty` for a transcription without speech, `canceled`, or `failed`
  with the error `code`); never the audio, the transcript or the text.

**`POST /audio/transcriptions`** — `audio.transcribe` · multipart
- Body `multipart/form-data`: exactly one recording in the part `file` + the `AudioTranscribeForm` fields. The route
  reads the multipart body itself; every refusal is `400 validation_error`: "Send exactly one recording." (a second
  file), "Attach the recording in the part named "file"." (none), "The part "file" must be a file." (a text part),
  "Unknown field "<name>".", "The field "<name>" is sent more than once.", "Only the part "file" may be a file ("<name>"
  is one).", or the field schema's issue (an invalid or empty `modelRef` / `language`).
- Size: at most 25 MB (`LIMITS.audioUploadBytes`, 26,214,400 bytes): a larger recording is `413 payload_too_large`
  "Recordings are limited to 25 MB." (`details.limitBytes: 26214400`); above 25 MB + 64 KB the body-limit middleware
  answers first ("The request body is larger than the limit of 25 MB.", the same `details`). A recording under 64 bytes
  is `400` "The recording is empty.".
- Accepted types, parameters such as `;codecs=opus` ignored (aliases in brackets): `audio/webm` (`video/webm`),
  `audio/ogg`, `audio/mp4` (`audio/x-m4a`, `video/mp4`), `audio/mpeg` (`audio/mp3`), `audio/wav` (`audio/x-wav`,
  `audio/wave`), `audio/flac` (`audio/x-flac`). The declared type must match the content (an EBML header with DocType
  `webm`, `OggS`, an `ftyp` box without an image brand, an `ID3` tag or an MPEG audio frame sync (AAC ADTS refused),
  `RIFF…WAVE`, `fLaC`); with `application/octet-stream` the content decides. A file part sent without a
  `Content-Type` header counts as `text/plain` and is refused. Refusals (`400`, issue path `file`): "The type <type>
  is not accepted: send a WebM, Ogg, MP4, MP3, WAV or FLAC recording.", "The recording does not match its type
  (<type>).", "The recording is not in a supported format: send a WebM, Ogg, MP4, MP3, WAV or FLAC recording."
  (`application/octet-stream`). Audio is accepted only here (chat uploads keep `UPLOAD_MIME_PATTERNS`).
- Model: `modelRef`, else the `transcriptionModelRef` setting. Language: `language`, else the `transcriptionLanguage`
  setting; `auto` sends none, a code goes through the provider's `transcriptionOptions` hook (a hook that throws or
  returns something invalid sends no hint).
- Timeout 120 s for the whole call, with at most one retry.
- Response `200 AudioTranscription` with `Cache-Control: no-store`: `text` trimmed (`''` when no speech was found; the
  AI SDK's `NoTranscriptGeneratedError` answers `''` too), `language` and `durationSec` as reported (else `null`).
- Errors: the multipart, size and type refusals above; the model, provider and cancel errors of the common rules.

**`POST /audio/speech`** — `audio.speech` · response `'binary'`
- Body `AudioSpeechBody` (`text` 1..4096 chars after trimming; else `400` on `text`).
- Model: `modelRef`, else the `speechModelRef` setting. Voice: `voice`, else the `speechVoice` setting, else the
  provider default (while `speechVoice` is set, a request cannot ask for the provider default). Only the text and the
  voice are sent (never an output format, a speed, instructions or a language: the browser applies `speechSpeed`).
- Timeout 60 s for the whole call, with at most one retry.
- Response `200` with the audio bytes exactly as the provider returned them: `Content-Type` from an allowlist
  (`audio/mpeg`, `audio/wav`, `audio/ogg`, `audio/webm`, `audio/mp4`, `audio/aac`, `audio/flac`; the reported type is
  normalized first, e.g. `audio/mp3` -> `audio/mpeg`, `audio/x-wav` -> `audio/wav`), `Content-Length`,
  `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`.
- Errors: `400 validation_error` (the text); `502 provider_error` "<Provider> returned no audio." or "<Provider>
  returned audio in a format that cannot be played (<type>)." (a type outside the allowlist, recorded as a provider
  failure); the model, provider and cancel errors of the common rules.

### 5.22 `projects.ts`

Projects (ADR-031, DTOs in section 4.20). Every route needs a session; adding a project also needs fresh auth (it gives
the session file and shell access to a folder), the other routes do not. Every change emits `project.changed`.

Common path errors (create and browse): the path is resolved to its canonical realpath first.
- `404 not_found` for a folder that does not exist, also a dangling link or a path through a file ("The folder <path>
  does not exist.").
- `400 validation_error` on `['path']` with the message as the issue: a relative path ("Use an absolute folder
  path."); a path that is not a directory, e.g. a file ("This path is not a folder."); a folder outside every allowed
  root ("Choose a folder inside the workspace folders."; `/etc` with the default root); a folder that cannot be read
  ("This folder cannot be accessed (permission denied)."); a symbolic link loop ("This path goes through a symbolic
  link loop."); a path the system refuses as too long ("This path is too long.").
- `400 validation_error` on `['path']` for a folder that overlaps the data directory (the subtree of the default root
  `<dataDir>/workspaces` excepted): "This folder is inside the harness-forge data directory." (a folder inside it) or
  "This folder contains the harness-forge data directory." (the data directory itself or a folder that contains it;
  to use harness-forge on its own repository, set `HF_DATA_DIR` outside it). Browsing a folder that contains the data
  directory is allowed (the data directory is not listed); with `newFolder`, the parent may contain it too, while the
  new folder itself must not overlap it.

**`GET /projects`** — `projects.list`
- Response `200 ListResponse<ProjectSummary>` sorted by name: every project with `available`, `issue`,
  `instructionsFile` and `chatCount` computed now.

**`POST /projects`** — `projects.create` · **fresh**
- Body `ProjectCreate`. The folder is resolved to its canonical realpath and checked (common path errors). With
  `newFolder`, `path` is the parent: the folder is created inside it (no intermediate folders) and used.
- Response `201 ProjectSummary`. Emits `project.changed`.
- Errors: the common path errors; `409 conflict` (`reason: 'exists'`) when a project already uses the folder ("A project
  for this folder already exists.") or the new folder already exists ("A folder with this name already exists."; a
  folder created by a failed request is removed again while it is still empty); `400 validation_error` on `['path']`
  when the new folder cannot be created ("The folder cannot be created here (permission denied).", "The folder name
  is too long.") or the server already has `LIMITS.projectsMax` (200) projects ("A server can have up to 200
  projects."); `403 forbidden` (fresh auth missing, `action: 'login'`; checked before the folder is touched).

**`PATCH /projects/:id`** — `projects.update`
- Params `ProjectParams`. Body `ProjectUpdate` (`name`, `instructions`; the folder never changes).
- Response `200 ProjectSummary`. Emits `project.changed`.
- Errors: `404 not_found` (unknown project, "Project <id> not found.").

**`DELETE /projects/:id`** — `projects.remove`
- Params `ProjectParams`. Detaches every chat of the project (their `projectId` becomes null) and deletes the project in
  one transaction; the folder and its files are never touched.
- Response `204`. Emits one `project.changed` with `project: null` (no `chat.updated` per detached chat: clients clear
  `projectId` themselves).
- Errors: `404 not_found`; `409 conflict` (`reason: 'run-active'`, `chatId`: the running chat) while a chat of the
  project runs ("A chat of this project is running. Stop it first, then try again.").

**`GET /projects/browse?path=`** — `projects.browse`
- Query `ProjectBrowseQuery`. Without `path`: the roots only (`path: null`, `parent: null`, no entries), each with
  `available`. With `path`: its subfolders (directories only; symbolic links, dot folders, `node_modules`, the data
  directory and names with control characters are not listed), in natural, case-insensitive name order (`app2` before
  `app10`), at most 500 (`truncated`), each with the `projectId` of a project that already uses it; `parent` is null
  at a root.
- Response `200 ProjectBrowse`.
- Errors: the common path errors.

### 5.23 `keys.ts`

Master key (ADR-034, DTOs in section 4.22). Both routes need a session; a rotation also needs fresh auth and the typed
confirmation.

**`GET /keys`** — `keys.get`
- Response `200 KeyStatus` (never the key). Read-only: it never writes `_keys` (section 4.22); during a rotation it
  answers once the new key is in place.

**`POST /keys/rotate`** — `keys.rotate` · **fresh**
- Body `KeyRotateBody` (`confirm` must be the literal `ROTATE`; else `400 validation_error` on `['confirm']`).
- Only for a key from `secret.key`. Checks in order: fresh auth, `confirm`, the key source (`env-key`), the maintenance
  lock (`busy`; while the rotation runs, `POST /chat` answers `409 busy` too), the key check (`key-mismatch`). Then it
  stops every run, re-encrypts every readable secret with a new random key in one transaction (unreadable secrets are
  left unchanged and counted), denies every open tool approval ("Expired after a key rotation.") and clears the
  pending-approval flags. A write-ahead `secret.key.next` (mode 0600) keeps the new key safe until it replaces
  `secret.key`; a crash in between is finished at the next boot. One info log line with the counts, never key text.
- Effects: every other session ends (the caller gets a new cookie and stays signed in and fresh); every share URL
  changes (owners copy the new links; the old URLs answer `404`); pending approvals are denied; runs were stopped;
  `key.rotated` is emitted, then every event stream closes. There is no downgrade to v1.2 after a rotation.
- Response `200 KeyRotationResult` + exactly one `Set-Cookie: hf_session=...` signed with the new key and keeping the
  caller's login time, so it stays fresh (no cookie when no password is set).
- Errors: `409 conflict` with `reason: 'env-key'` ("The master key comes from HF_MASTER_KEY and cannot be rotated
  online. Stop the server and run "rotate-key" with HF_NEW_MASTER_KEY set (pnpm key:rotate)."), `reason:
  'key-mismatch'` ("The master key in use does not match the key the secrets were written with; a rotation would lose
  them. Restore the original key first.") or `reason: 'busy'` ("Another data task is running. Try again when it
  finishes."); `403 forbidden` (fresh auth missing, `action: 'login'`).

### 5.24 `changes.ts`

The changes panel, revert, undo and rewind of a project chat (ADR-036, ADR-037; DTOs in section 4.23). Every route needs
a session; none needs fresh auth. The routes work on the chat's **current** project (rows recorded while the chat
belonged to another project are ignored); every path resolves through the workspace path guard (realpath containment,
no `.git`).

Common errors:
- `404 not_found` for an unknown chat ("Chat <id> not found.").
- A chat without a project, a project that no longer exists, or a folder that cannot be opened: `changes.list` and
  `changes.git` answer `200` with `available: false` and the `reason`; every other route answers `400 validation_error`
  with the message of the project service ("The project of this chat no longer exists.", "The project folder <path> is
  not available: <issue>").
- Revert, undo and rewind: `409 conflict` (`reason: 'run-active'`, `chatId`: the running chat) while **any** chat of the
  project runs ("A chat of this project is running. Stop it first, then try again."); nothing is written. The `GET`
  routes also answer during a run.

Writes: each file is written under a per-file lock shared with the agent tools; its current state is stored first, then
the earlier state is written atomically (a re-created file gets its old mode back) or the file is removed; every write is
journaled under one batch id right away, so an interrupted batch can be undone or run again. A batch that wrote
something emits `workspace.changed` (`source` = `revert`, `undo` or `rewind`, with `batchId`).

**`GET /chats/:id/changes`** — `changes.list`
- Params `ChatParams`.
- Response `200 ChatChanges`: one entry per path the chat changed (net change of the base against the disk), most
  recently changed first, at most 500 (`truncated`); line counts for the first 200 text files of at most 256 KiB;
  `untracked` counts the shell commands and other workspace tool calls the journal cannot restore.

**`GET /chats/:id/changes/diff?source=chat|git&path=`** — `changes.diff`
- Params `ChatParams`. Query `ChangeDiffQuery`.
- `source=chat`: the base (before the chat first changed the file) against the disk. `source=git`: the HEAD blob
  against the disk (an untracked or added file against nothing, a deleted file against nothing, a renamed file against
  HEAD of `origPath`; with an unborn HEAD every file is added). Git's own diff is never run (diffs are computed by the
  server); each side at most 1 MiB (`tooLarge`), binary sides give no diff.
- Response `200 FileDiff`.
- Errors: `404 not_found` (`source=chat`: a path the chat never changed); `400 validation_error` (`source=git`: the git
  view is not available, with its reason).

**`GET /chats/:id/git`** — `changes.git`
- Params `ChatParams`.
- Runs `git status` of the project folder (porcelain v2, untracked files included, submodules ignored) through the
  hardened git runner: an argument array without a shell, a scrubbed environment, `GIT_CEILING_DIRECTORIES` above the
  allowed root, file system monitors, hooks, external diff and pager, filter drivers and optional locks disabled, 15 s
  timeout, output capped at 8 MiB. The index is never touched. A project in a subfolder of a repository lists only its
  own files (`prefix`).
- Response `200 GitStatus`; `available: false` with `reason`: `no-project`, `folder-unavailable`, `git-missing` (git is
  not installed), `not-a-repo`, `refused` (git refused the repository, e.g. "dubious ownership" of a folder owned by
  another user, common with Docker bind mounts; `safe.directory` is not overridden), `timeout`, `failed`.

**`POST /chats/:id/changes/revert`** — `changes.revert`
- Params `ChatParams`. Body `ChangeRevertBody`.
- `source: 'chat'` writes the file back to its base (removes it when the chat created it). `source: 'git'` writes back
  the HEAD content (mode `100755` stays executable): an untracked or added file is removed, a renamed file is restored
  at `origPath` and removed at `path`. The current state is stored first, so the revert is one undoable batch.
- Response `200 RestoreResult` (a base that is not stored: `skipped` with `reason: 'unavailable'`, `batchId: null`).
- Errors: `409 conflict` (`reason: 'stale'`) when the disk state is not `expectedSha` ("The file changed since it was
  shown. Refresh and try again."); `404 not_found` (`source: 'chat'`: a path the chat never changed); `400
  validation_error` on `['path']` for a path the guard refuses, and (`source: 'git'`) for a conflicted file, a symbolic
  link, a submodule or a path with a `filter` attribute (Git LFS), or when the git view is not available; the common
  errors.

**`POST /chats/:id/changes/undo`** — `changes.undo`
- Params `ChatParams`. Body `ChangeUndoBody`.
- Writes back the states every file of the batch had before it (the batch of a revert, a rewind or an undo); a file
  that changed since the batch wrote it is a conflict (`skip` or `force`). The undo is a new batch (undo it to redo).
- Response `200 RestoreResult`.
- Errors: `404 not_found` (a batch that is not one of this chat, "Change batch <batchId> not found."); the common
  errors.

**`GET /chats/:id/rewind?messageId=`** — `changes.rewindPreview`
- Params `ChatParams`. Query `RewindQuery`.
- What `POST /chats/:id/rewind` would do now: every file the chat changed since the user message was sent (section
  4.23), with its action and conflict, and the shell commands and other tool calls in that range that a rewind cannot
  undo. Writes nothing.
- Response `200 RewindPreview` (no files: nothing to restore).
- Errors: `404 not_found` (`messageId` not in the chat, "Message <messageId> not found in chat <id>."); `400
  validation_error` on `['messageId']` for a message that is not a user message; the common errors.

**`POST /chats/:id/rewind`** — `changes.rewind`
- Params `ChatParams`. Body `RewindBody`.
- Restores every file of the preview, the most recently edited first: `restore` writes the earlier content, `delete`
  removes a file the chat created, `unchanged` files are listed as such, `unavailable` ones are skipped; a file whose
  disk state differs from the chat's last recorded change is skipped (`conflict`) unless `conflicts: 'force'`. The
  conversation is not changed.
- Response `200 RestoreResult` (`batchId: null` when nothing was written).
- Errors: as `changes.rewindPreview`, plus `409 run-active`.

### 5.25 `shell-rules.ts`

Shell rules (ADR-038, DTOs in section 4.24). Every route needs a session; none needs fresh auth (a session can already
approve its own shell calls). Rules are read when a run starts. Emits no event.

**`GET /shell-rules`** — `shellRules.list`
- Response `200 ShellRuleList`: every rule, the global ones first, then by project and prefix.

**`POST /shell-rules`** — `shellRules.create`
- Body `ShellRuleCreate`. The prefix is checked with `parseShellRule` and stored in its canonical form.
- Response `201 ShellRule`.
- Errors: `400 validation_error` on `['prefix']` with the parser's message for a refused prefix (section 4.24); `400
  validation_error` when the scope (the project, or the global list) already has 200 rules
  (`LIMITS.shellRulesPerScopeMax`); `404 not_found` (unknown `projectId`, "Project <id> not found."); `409 conflict`
  (`reason: 'exists'`) when the scope already has the same canonical prefix ("This rule already exists.").

**`DELETE /shell-rules/:id`** — `shellRules.remove`
- Params `ShellRuleParams`. There is no edit: remove a rule and add another.
- Response `204`.
- Errors: `404 not_found` (unknown rule, "Shell rule <id> not found.").

## 6. Chat stream protocol

`POST /api/chat` returns an **AI SDK v7 UI message stream**: `createUIMessageStreamResponse({ stream,
consumeSseStream })`, where `stream` is built with `createUIMessageStream` for every run since Phase 6 (section 6.3),
so generated files are stored before they are streamed and the saved message equals the streamed one. Verify every AI
SDK name against the installed `node_modules/ai` types before implementing.

### 6.1 Client setup (reference)

```ts
import { DefaultChatTransport, lastAssistantMessageIsCompleteWithApprovalResponses } from 'ai'
import { useChat } from '@ai-sdk/vue'
import { createMessageId, harnessDataSchemas, messageMetadataSchema,
  type ChatRequestBody, type HarnessUIMessage } from '@harness-forge/shared'

const chat = useChat<HarnessUIMessage>({
  id: chatId,                                   // uuidv7 (createChatId() for a new chat)
  messages: detail?.messages ?? [],             // ChatDetail.messages
  throttle: 50,                                 // optional: batch reactive updates (ms)
  generateId: createMessageId,                  // user message ids: msg_ + 16 chars
  messageMetadataSchema,
  dataPartSchemas: harnessDataSchemas,
  sendAutomaticallyWhen: lastAssistantMessageIsCompleteWithApprovalResponses,
  transport: new DefaultChatTransport({
    api: '/api/chat',
    prepareSendMessagesRequest: ({ id, messages, trigger, messageId }) => {
      const message = messages[messages.length - 1]!
      const target = trigger === 'regenerate-message'
        ? { messageId }                                    // the reply to regenerate (undefined = active leaf)
        : message.role === 'user'
          ? { parentId: messages.at(-2)?.id ?? null }      // new or edited user message: its parent
          : {}                                             // approval continuation: neither
      return {
        body: {
          chatId: id, message, trigger, ...target,
          modelRef, reasoningEffort, toolMode,             // current composer state
        } satisfies ChatRequestBody,
      }
    },
  }),
})
// resume: @ai-sdk/vue 4 has no `resume` option (React only); on mount, when the chat has an active run
// (ChatSummary.running, or a run.started event), call:
void chat.resumeStream()                        // GET /api/chat/:id/stream, 204 -> nothing to do
// approvals: chat.addToolApprovalResponse({ id: part.approval.id, approved, reason? })
// stop:      await client.chat.stop({ params: { id } }); chat.stop()
```

### 6.2 What `message` contains

The messages of a chat form a tree (ADR-023): editing a message or regenerating a reply adds a sibling **version**;
nothing is deleted. `ChatDetail.messages` is the active path, `ChatDetail.branches` lists the versions, and
`POST /chats/:id/branch` switches between them.

| User action | `useChat` call | `trigger` | `parentId` / `messageId` | `message` (last UI message) | Server behavior |
|---|---|---|---|---|---|
| Send | `sendMessage({ text, files })` | `submit-message` | `parentId` = the previous message (`null` for a first message; omitted = the active leaf) | new user message | stored under `parentId` and made the active leaf; pending approvals on that path resolved as denied (`superseded`, `data-notice` `approvals-superseded`) |
| Edit | the local messages are cut before the edited one, then `sendMessage({ text, files })` (a new id) | `submit-message` | `parentId` = the edited message's parent | new user message | a sibling version of the edited message; the old version and its later messages stay stored (switch back with `POST /chats/:id/branch`) |
| Regenerate | `regenerate({ messageId? })` | `regenerate-message` | `messageId` = the reply to regenerate, or a user message to answer (default: the active leaf) | the user message it answers | a new reply as a sibling of the old one (the old reply is kept); the answered user message is the active leaf until the new reply is stored |
| Approval continuation | automatic (`sendAutomaticallyWhen`) | `submit-message` | neither | the active leaf assistant message with `approval-responded` parts | merge only approval decisions by `approval.id`; continue the same assistant message |

Rejected before streaming: a user message sent with `messageId` (`400`, in-place edits were removed), `parentId` on a
regenerate or a continuation (`400`), a regenerate target not answered by a user message (`400`), an unknown
`parentId` or `messageId` (`404`: the web refetches the chat, its local path is stale), a continuation that is not the
active leaf (`404`), and a user message id that is already stored (`409`, `reason: 'exists'`). The web never sends
the id of a user message whose request failed with an HTTP error (the server stored nothing).

With an image model (ADR-028) Send, Edit and Regenerate work the same (each is an image turn); an approval
continuation needs a chat model (`400` on `['modelRef']` with an image model). `imageOptions` travel next to
`modelRef` (section 6.8). A version is deleted with `DELETE /chats/:id/messages/:messageId` (ADR-030), never through
`POST /chat`.

User text parts: plain text (slash commands are expanded server-side, see ARCHITECTURE.md 6.1). File parts:
`{ type: 'file', mediaType, filename, url: '/api/files/<id>' }` from `POST /files`; the server loads the bytes
only for models with `vision` (images) or `pdf` capability, otherwise the part is kept for display and a
`data-notice` explains it was not sent.

### 6.3 Response

- Model runs: `const ui = toUIMessageStream({ stream: result.stream, tools, originalMessages, generateMessageId: () =>
  assistantId, sendReasoning: true, sendSources: true, messageMetadata, onError })` with **no** end callback of its own
  (`sendSources` defaults to false in v7; the web renders sources, so it must be true). `assistantId` is created with
  `createMessageId()` before the stream starts (the continued message's id for an approval continuation). Headers come
  from `UI_MESSAGE_STREAM_HEADERS`.
- Phase 6 (ADR-028): the end callback of `toUIMessageStream` would save the chunks it produced itself, before generated
  files are stored, so every run is returned through `createUIMessageStream({ originalMessages, generateId: () =>
  assistantId, onError, onEnd, execute })`: for a model run `execute` is `({ writer }) =>
  writer.merge(ui.pipeThrough(storeGeneratedFiles(...)))`, a transform that stores every generated `file` /
  `reasoning-file` chunk and appends the `generate_image` images (section 6.8); image turns (section 6.8), reply
  commands and failures before the model call write their chunks in `execute` themselves. The single `onEnd` saves
  what was streamed. The notices of a run (`data-notice`) follow the `start` chunk, except `generated-file-dropped`,
  which takes the place of its file.
- Status `200`, headers `Content-Type: text/event-stream`, `x-vercel-ai-ui-message-stream: v1`,
  `Cache-Control: no-cache`, `X-Accel-Buffering: no`, `X-Request-Id`.
- Body: SSE events `data: <UIMessageChunk JSON>\n\n`, terminated by `data: [DONE]\n\n`.
- Chunk types used (v7): `start` (with `messageId`, the id the reply is stored under: server-generated, or the
  continued message's id for an approval continuation; and `messageMetadata`), `start-step`, `finish-step`,
  `text-start` / `text-delta` / `text-end`, `reasoning-start` / `reasoning-delta` / `reasoning-end`,
  `tool-input-start` / `tool-input-delta` / `tool-input-available` / `tool-input-error`, `tool-approval-request`,
  `tool-output-available` / `tool-output-error` / `tool-output-denied`, `source-url`, `source-document`, `file`
  (always an `/api/files/<id>` URL, never a `data:` URL), `reasoning-file` (same rule), `data-notice`,
  `message-metadata`, `error`, `abort`, `finish` (with `messageMetadata`). The web consumes them only through
  `useChat`; it never parses chunks itself.

### 6.5 Metadata and errors

- `start` carries `messageMetadata: { modelRef, startedAt }` (an image turn adds `image: { n, aspectRatio?, inputs }`);
  `finish` carries `{ finishedAt, durationMs, reasoningMs?, usage, costUsd?, finishReason }`. Both merge into
  `message.metadata` (`MessageMetadata`). The estimated cost of `generate_image` outputs is added to `costUsd`. An image
  turn's `finish` keeps `image` (plus `revisedPrompt` when the provider reported one), has `usage` = `{ inputTokens,
  outputTokens, totalTokens }` only when the provider reported token counts, `costUsd` only when it could be estimated
  (section 4.18) and `finishReason: 'stop'`. An aborted message is persisted with `aborted: true`; the live client
  learns it from the `abort` chunk and `run.finished`. A failed or aborted image turn is saved with its `image` metadata
  and `finishedAt` but without files.
- **Before streaming** (validation, `provider_not_configured`, `conflict`, `not_found`): normal JSON error
  response; `DefaultChatTransport` throws an `APICallError` (`statusCode`, `responseBody` = envelope JSON,
  `message` = the same text) that `useChat` exposes as `chat.error`.
- **During streaming**: `onError` maps the error (section 2.3) and returns the envelope JSON (`JSON.stringify(e.toJSON())`), sent as
  `{ "type": "error", "errorText": "{\"error\":{\"code\":\"auth_invalid\",...}}" }`; the same `HarnessErrorInit` is
  persisted in `metadata.error`. Tool execution errors do not end the stream: they become `output-error` parts.
- The web always calls `HarnessError.from(chat.error)` (and reads `metadata.error` of stored messages) and maps
  `code` / `action` to UX: `configure-provider` -> "Open settings", `refresh-models` -> refresh, `retry` -> Retry
  (a regenerate of the failed reply; a user message whose request failed before streaming is sent again as a new
  message), `login` -> login.

### 6.6 Resume and stop

- `GET /api/chat/:id/stream`: `204` when no run is active; otherwise the same stream format, replayed from the
  first chunk of the active run, then live chunks. At most one run per chat, so resume needs no run id. While a
  run is active, `GET /chats/:id` returns the path to the leaf committed when the run started (the new or answered
  user message, or the continued assistant message) and excludes the in-flight reply (an approval continuation
  shows the pre-continuation message), so the replay is applied exactly once on top of it; the web refetches the
  chat on `run.finished` unless it is streaming it itself (ARCHITECTURE.md 6.3). `POST /chats/:id/branch` and
  `DELETE /chats/:id/messages/:messageId` are refused with `409 conflict` (`reason: 'run-active'`) while a run holds
  the chat.
- `POST /api/chat/:id/stop`: aborts the run (`abort` chunk to every reader), persists the partial message with
  `aborted: true`; returns `{ stopped }`. The web calls it before `chat.stop()`; a client abort alone only
  disconnects (the run continues and stays resumable).
- A second `POST /api/chat` for a chat with an active run gets `409 conflict` (`reason: 'run-active'`).

### 6.7 Approvals

- Approval decisions come from the server-side approval function (ARCHITECTURE.md 6.2) passed as
  `streamText({ toolApproval })`; `experimental_toolApprovalSecret` (HKDF `approval` subkey) signs approval
  requests so a response is valid only for the exact tool call and input.
- The continuation request carries the whole last assistant message, but the server merges only
  `approval.approved` / `approval.reason` per `approval.id` into the stored copy; any other client change is
  ignored.
- Allow with "Always allow {tool}" checked = `PATCH /api/tools/:name` `{ override: 'allow' }` +
  `addToolApprovalResponse(...approved: true)`. Not offered for tools with workspace access `execute` (the server
  refuses that override, section 5.12): their card offers "Always allow commands starting with <prefix>" (This project |
  All projects) instead = one `POST /api/shell-rules` per suggested prefix (section 5.25), then the normal approval
  (the approval format is unchanged).
- Resolution order: the user's tool override (`allow` / `ask` / `deny`), then the `tool.approve` hook, then a policy
  `deny`, then the permission mode (`ToolMode`) with the tool's policy and workspace access (Phase 7, ADR-032):

  | Mode | Runs without asking | Asks |
  |---|---|---|
  | `off` | (no tools are sent to the model) | - |
  | `ask` | `safe` | everything else |
  | `edits` | `safe`, and `ask` with workspace access `write` | everything else, `always` included |
  | `auto` | everything except `always` | `always` |

  A policy function resolves first (e.g. `write_file` on a hidden path is `always`, so it asks in every mode);
  `shell` (policy `ask`, access `execute`) asks in `ask` and `edits` mode, except (Phase 8, ADR-038) a command whose
  every segment matches a shell rule of the project or the global list: its policy is then `safe`, so it runs without
  asking in `ask` and `edits` (`allowedBy` in the output). The rules are read when a run starts; an override `ask` or
  `deny` and the `tool.approve` hook still win, and a stored `allow` override of an `execute` tool is ignored.
- Approvals on other versions of a chat stay pending: switching back to such a version sets `pendingApproval` again,
  and the approval card is live because the continuation targets the active leaf.

### 6.8 Images (ADR-028)

- **Image turn** (a model of `kind: 'image'`), one `ImageService.generate` call:
  1. `start` (metadata `{ modelRef, startedAt, image: { n, aspectRatio?, inputs } }`, so the web shows `n` placeholder
     tiles at the aspect ratio), followed by the run's notices (e.g. `attachments-unsupported`);
  2. `start-step`;
  3. a `message-metadata` keep-alive with the same start metadata every 15 s while the provider works (proxies close
     idle connections);
  4. one `file` chunk per stored image (`{ url: '/api/files/<id>', mediaType }`), then one inline
     `generated-file-dropped` notice when some images were refused (the reply may hold only that notice);
  5. `finish-step`;
  6. `finish` (`finishReason: 'stop'`, metadata with `usage?`, `costUsd?`, `image.revisedPrompt?`, section 6.5).

  A failure is an `error` chunk (the envelope; the message keeps `metadata.error`); Stop is an `abort` chunk (saved with
  `aborted: true`); both keep `metadata.image` and `finishedAt` but no files. Resume replays the same chunks (the images
  are stored before they are streamed, so the buffer holds URLs only, never bytes); a regenerate adds a version.
- **Chat models with image output**: the `definition.imageParams({ n: 1, aspectRatio, inputs: 0 }, model)` provider
  options are deep-merged under the reasoning options of the call; every generated `file` / `reasoning-file` chunk with
  a `data:` URL is stored first and re-sent with its `/api/files/<id>` URL (provider metadata such as Gemini thought
  signatures kept); anything else is replaced by an inline `data-notice` (`generated-file-dropped`). No `data:` URL is
  ever streamed or saved.
- **`generate_image`**: right after the final `tool-output-available` chunk of the tool (from `core-tools`, output
  parsing with `generateImageToolOutputSchema`, every URL naming its stored image) one `file` chunk per image follows,
  also on an approval continuation, and the tool's `costUsd` is added to the cost of the message.
- **File names**: a UI `file` chunk carries no name, so only the saved `file` parts of generated images get `filename`
  (`image-<n>.<ext>`, or the name of an identical file stored earlier: generated files are deduplicated by content).
- `imageOptions` (`ChatRequestBody`): `n`, `aspectRatio`, `editPrevious` for image models; `aspectRatio` only for chat
  models with image output; the web sends it only for image-capable models (`400` otherwise, section 5.10).

## 7. Server events (`GET /api/events`)

- Session required. Response `200` with `Content-Type: text/event-stream`, `Cache-Control: no-cache`,
  `Connection: keep-alive`, `X-Accel-Buffering: no`. The web opens one `EventSource('/api/events')` per tab
  (`plugins/events.client.ts`).
- Wire format: first `retry: 3000`, then per event:

  ```
  id: 42
  event: chat.updated
  data: {"type":"chat.updated","data":{...ChatUpdatedData},"at":1759000000000}

  ```

  `id` is a per-process increasing integer; `event` equals `type`; `data` is the full `ServerEvent` JSON.
- Heartbeat: a comment line `: ping` every **25 s**. Each heartbeat re-checks the session: the stream ends when it
  is no longer valid (password changed, logged out, expired). Shutdown also ends every stream, and so does a master-key
  rotation (right after `key.rotated`) or a password change (Phase 7).
- No replay: `Last-Event-ID` is ignored. After a reconnect (`EventSource` `open` following an `error`) the web
  refetches its stores. A slow connection whose queue exceeds 256 events is closed by the server.

| Event | Emitted when | `data` | Web reaction |
|---|---|---|---|
| `chat.created` | `POST /chats`, the first `POST /chat` for a new chat id, or `POST /data/import` (one per imported or copied chat) | `ChatSummary` | chats store: insert |

Phase 8 adds `workspace.changed`; shell rule changes and the automatic file sweep emit nothing. Phase 7 adds
`project.changed` and `key.rotated`; moving a chat to another project is a `chat.updated` (its summary carries
`projectId`), the file cleanup emits nothing. Phases 5 and 6 add no event types: bulk import and delete-all
report every chat through `chat.created` /
`chat.deleted`, a version switch or delete through `chat.updated`; share link actions, dictation and read-aloud emit
nothing (the owner UI refetches). Since Phase 6 `chat.updated` carries the active leaf (`ChatUpdatedData`, ADR-030),
so another tab that shows the chat follows a version switch; deleting a version that is not on the active path emits
`chat.updated` with the unchanged leaf, so other tabs do not refetch and show stale version counters until they reload
the chat.

Server registration order note: within `plugins.ts`, `plugin-install.ts`, `plugin-drafts.ts` and
`plugin-files.ts`, static paths (`/plugins/inspect`, `/plugins/install`, `/plugins/scaffold`,
`/plugins/drafts/test`) never collide with `/plugins/:id...` routes because they differ in method or segment
count; keep it that way when adding routes. The `data.ts` paths are all static (`/data`, `/data/export`,
`/data/import`, `/data/delete`, `/data/cleanup`), as are the `audio.ts` paths (`/audio/transcriptions`,
`/audio/speech`) and the `keys.ts` paths (`/keys`, `/keys/rotate`); `projects.ts` has no `GET /projects/:id`, so
`GET /projects/browse` never meets a param route of the same method (`PATCH` / `DELETE /projects/:id` differ in method);
the owner routes `/shares...` and the public routes `/share/:token...` differ in their first segment, and
`DELETE /chats/:id/messages/:messageId` differs from `DELETE /chats/:id` in its segment count, so none of them shadows
another. The `changes.ts` routes live under `/chats/:id` too (Phase 8): `/chats/:id/changes`, `/chats/:id/git` and
`/chats/:id/rewind` differ from `/chats/:id/export` and `/chats/:id/branch` in their static third segment, and
`/chats/:id/changes/diff`, `/chats/:id/changes/revert` and `/chats/:id/changes/undo` from every `chats.ts` route in
their static segments or their method; `shell-rules.ts` paths start with their own segment (`/shell-rules`).
